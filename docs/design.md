# DesertBird design

DesertBird is a keyboard-first Thunderbird add-on, and it works in Betterbird too. It replaces setups that load key files into Thunderbird through an autoconfig file. It follows the DesertFox design: one command registry, one validator, the keymap as data, no string eval and a native host with fixed verbs.

The goals:

- It installs as one signed add-on and needs no autoconfig file, no package-manager hook and no second key add-on.
- Every default binding maps to a registry command (the split table below).
- Most commands run on standard MailExtension APIs. An Experiment is the privileged part of a Thunderbird add-on, and it runs chrome code. This one does only what no standard API can do, through a fixed set of verbs.

## Principles

- Same principles as DesertFox `docs/design.md`. Define each command once in the registry, and check args only in the one `check_args`. Keep the keymap as data and never evaluate strings. Give the native host and the Experiment fixed verbs only. Keep no state only in memory, and write a migration for every change to stored data.
- Hybrid add-on: a MailExtension plus one Experiment. A pure MailExtension cannot take plain keys in the main mail window, because the `commands` API takes modifier chords only.
- The Experiment holds no command logic of its own. It has two parts. The chrome runtime holds the key matcher, the modes and the instant commands, like DesertFox `content.js`. The verb table is a fixed list of calls the background can make. A new verb needs a reason in the commit, the same rule as a new native host verb.
- Bindings that run code from a string do not exist. The keymap is data.
- The external editor goes through the DesertFox native host verbs `editor_start` and `editor_collect`, not a terminal launched through XPCOM. The host owns the editor command, so no request carries argv.
- Code home: this repository. The core shared with DesertFox (`define`, the checks, `check_args`, the parser, the prefix tree) is a pinned copy in `vendor/desertfox/`, made by `tools/vendor_desertfox.sh`. The copy lets DesertBird build from its own repository and lets the store reviewer match every file against the pin. There is no third repository.

## Architecture

The parts map onto DesertFox like this:

| DesertBird part | DesertFox counterpart | Holds |
| --- | --- | --- |
| Background page | Background page | The registry, the handlers that use standard APIs, keymap compile, config, storage |
| Chrome runtime (Experiment parent script) | `content.js` | The key listener in each mail and compose chrome window, the prefix tree matcher, modes, counts, and the `runs_in: "chrome"` handlers |
| Chrome verbs (Experiment API schema) | None (new) | A fixed table of privileged operations that background handlers call |
| `messageDisplayScripts` | `content.js` in a page | Keys inside the message body, and hints there when the parent cannot label the message (see "Hints in a message"), which runs in a content process the chrome listener cannot see. Measured: for local mail the message pane is not remote and a chrome listener sees its keys (see [`thunderbird-behavior.md`](thunderbird-behavior.md), Message pane process) |
| `composeScripts` | `content.js` in a field | Ctrl+E inside the compose body (built). The modes, the other keys and the mode label of a compose window are in the chrome runtime (`composewin`, see Compose normal mode); hints are not |
| Overlay page in the chrome window | `cmdline.html` in a remote `browser` element and the `ui` bundle | Command line, completion, which-key and toasts |
| Native host | Native host | Config read (`read_config`) and the external editor (`editor_start`, `editor_collect`) |

Registry changes from DesertFox:

- `runs_in` takes `background`, `chrome`, `message` or `compose`. A command runs on one side only.
- `chrome` holds only commands that must answer a held key at once: the motions, page moves, counts and mode changes. The DesertFox admission rule for `content.js` applies to the chrome runtime as written, with its own size guard.
- `needs` lists the chrome verbs a background handler calls (`needs: ["view.rows", "view.select"]`). The router refuses with a message when the Experiment is missing or failed to load, never a silent no-op.
- A build step writes the split table below from the registry, the way DesertFox generates `docs/keymap.md`. A test fails when a handler calls a chrome verb its `needs` does not list.

## Chrome verbs

This list is the whole privileged surface. Each verb takes typed args and is checked against the Experiment schema.

- `keys.install {tree, settings}`, `keys.set_mode {mode}` and the `keys.onInvocation` event: the chrome runtime matches keys locally and sends finished invocations, the typed prefix of a half-typed sequence (`pending`) and the start and end of visual mode and resize mode (`mode`).
- `view.rows {first, last}`: built as `app.viewRows`, with `app.viewThread`, `app.viewAllThreads` and `app.viewScroll` for the three below, all in the on-demand `app` API. The key script, which loads at startup, holds none of them. `viewRows` also returns the current row. The visible thread rows with index, message id, depth, collapsed, unread and the message flags word. `view.select {anchor, end}`, `view.scroll {row, position}`, `view.thread {row, open}` and `view.all_threads {open}`.
- `folder_tree.expand {open, extent}`: built as `folderpane.fold`, in the on-demand `folderpane` API. `extent` is `row` (the selected row, for `h` and `l`), `all` (`z M`, `z R`) or `parent` (no default key). It answers false, doing nothing, unless the folder pane has the focus, which is how `h`, `l`, `z M` and `z R` tell the two panes apart. A failed load of its script leaves `h`, `l`, `z M` and `z R` acting on the thread list. It takes no folder because the selected row is the cursor.
- `folderpane.viewRowCount`: the rows the message list shows now (`gDBView.rowCount`). It sits in the on-demand `folderpane` API and not in `keys`. The command line reads it once at open for the `[n/m]` widget. The line's status widgets differ from DesertFox, which shows the address, the scroll place and the tab place of a page: DesertBird shows the folder and the row place, a pinned `status.ts` would carry only dead Firefox code, and the widgets arrive in their own message after the focus is set.
- `folder_tree.focused {}`: built as `folderpane.focused`. It answers whether the folder pane has the focus. The background asks it on `/`, so one key serves both panes. No `select` verb exists: `mailTabs.update` with the folder opens the closed folders above it and selects its row, and `pane.focus` returns the focus to the folder pane.
- `pane.resize {direction}`: built as `app.paneResize {windowId, direction, steps}` in the on-demand `app` API. `direction` is `left`, `right`, `up`, `down` or `reset`, and `steps` is the count: one step is 24 CSS pixels. It moves the border of the focused pane by direction, so `l` in the message pane on the right makes it narrower. A border is a splitter that touches the focused pane on the axis of the move and overlaps it on the other, whichever pane the splitter sizes, so the message pane in the classic layout moves the folder splitter on its left. A pane with a border on each side (the thread list in the vertical layout) moves the one after it. The verb sets the size on the splitter and fires `splitter-resized` on it, the event that ends a drag, so `PaneLayout` stores the size in XULStore and a restart keeps it. The size the grid gives is read back and stored, as after a drag, so a pane stops at the grid minimum and a key never collapses a pane (only a drag below the `collapse-` size does). It answers false when the focused pane has no border on that axis (the layout has none, a pane is collapsed, the folder splitter is disabled in a synthetic view). `reset` sets both splitters to no size and removes the four stored values (width and height of `folderPaneBox` and `messagepaneboxwrapper`), and fires no event, because the handler would store the empty size. The command has no default key. The resize mode on `w r` runs it. A page tab and a message tab have no splitters and no key.
- `pane.focus {pane}`: built as `app.paneFocus`, where pane is `folders`, `threads`, `message`, or `left` and `right` for the pane beside the focused one. It answers false, leaving the focus where it was, when the target is a collapsed pane, a message pane with no live body script, or past an end.
- `app.command {name}`: built as `app.appCommand`. One name from a fixed allowlist of Thunderbird commands: `cmd_openConversation` and the four step commands `cmd_nextMsg`, `cmd_previousMsg`, `cmd_nextUnreadMsg` and `cmd_previousUnreadMsg`. For a step command it also answers false when the view has no next or previous (unread) message, because Thunderbird answers enabled at the ends, stays put or wraps, and never says so. It runs on the command controller of the page that shows the message (the mail tab, a message tab or a message window). It answers false when Thunderbird has the command disabled. Never a free string.
- `app.open_page {page}`: built as `app.appOpenPage`. One key of a fixed table (`addons`, `themes`, `config`), never a URL. The counterpart of the DesertFox host verb `open_firefox_page`.
- `hints.sendEnter {windowId}`: built, in its own bundle. A trusted Enter key press (the key is fixed, no text) in the window, for the link a hint pick in a message focused. A script `click()` skips Thunderbird's check for a link that lies about its address, so the body script asks for a real key instead.
- `hints.pick {windowId, colors, action?}`: built, in the same bundle. Labels the buttons, tabs, fields, folder rows and message rows of the front mail tab (in any other tab, the controls of the window and of the tab's own page, see Keys in the other tabs), each label drawn in its own chrome document (the window, `about:3pane` and `about:message`) in a closed shadow root, and holds the keys until a label is typed in full or the labels end. The one verb covers collecting, narrowing and acting, because the key sink must sit in the same bundle as the labels: a hint letter is also a command key (`a`, `d`), and a round trip to the background per key would let it run. The `action` argument (`focus`, `activate`, `yank`; absent is `activate`) says what the typed label does. A yank writes the text with `nsIClipboardHelper` in the parent, inside the key event, so no round trip to the background sits between the key and the clipboard. The parent reads the text from the page and the call never carries any. The message and compose content scripts hold their own hints.
- `zoom.get {windowId}` and `zoom.set {windowId, level}`: built, in the on-demand `zoom` API. They read and set the zoom of the browser the window's `getBrowser()` names, through Thunderbird's own `ZoomManager`: the message pane in the mail tab, a message tab and a message window, and the page of the address book, settings and content tabs. `get` answers null and `set` false where there is none (calendar, tasks, a mail tab with no message). `level` is a number from 0.3 to 5, checked by the schema.
- `composewin.install {composeTree, allowSend}` and the `composewin.onInvocation` event: built, in the `composewin` API. The key runtime of the compose windows matches keys locally and sends only finished background invocations. Its chrome leaves come from a fixed table: `compose.focus {field}` (`focusMsgBody()`, `showAndFocusAddressRow(row)`, the subject's `focus()`), `compose.close` (`goDoCommand("cmd_close")`) and `compose.send` (`goDoCommand("cmd_sendWithCheck")`, only while `allowSend` is true). The two commands are fixed names, never a string from the caller.
- `overlay.mount` and `overlay.unmount`: the extension page that draws the command line, which-key and toasts in the chrome window.
- `overlay.setModeLabel`: the mode label at the start of the status bar. The args are a window id, three enums (the mode, the `mode_indicator` setting and the `mode_indicator_style` setting) and the label colors as `#rrggbb` for both color schemes. The parent owns the text and picks the scheme Thunderbird shows in the window. The Experiment draws it because a page cannot sit inside the status bar. It reads the focus itself for insert mode, since the key runtime does not track insert.

## Decisions

- ESR floor: 153 ESR, so `strict_min_version` is 153.0. ESR 128 is end of life, Betterbird retired its 140 line, and each extra base costs a test run on the chrome verbs. Revisit when a user on an older ESR asks.
- HTML compose conversion: a vendored `marked` (Markdown to HTML) and `turndown` (HTML to Markdown), both MIT. This needs no pandoc install and no host verb that spawns a process. The editor itself still needs the host. Revisit if the quote split (see build order 4) still loses structure.
- Bridge socket: built before the first listing, so the first listing asks for `nativeMessaging` once. The bridge is the DesertFox bridge host and socket. It is off by default behind the `bridge` setting and gives the mode in the bar, `run` from outside and the CLI verbs. The add-on side, its never-list and its frames are in [`src/background/bridge/README.md`](../src/background/bridge/README.md). `test/registry.test.ts` holds the audited set of `bridge: true` commands. Reads (folders, headers, bodies, attachment names) each sit behind their own default-off share setting, checked in the add-on at each request. A body leaves only as cleaned text marked untrusted, and an encrypted body never leaves. The table of read frames is in the same README. A `draft` frame sits behind its own default-off `bridge_allow_drafts` setting. It saves a plain-text draft to Drafts through a compose window that it closes again, and answers only ok or a fixed refusal. The bridge never sends: `compose.send` has `bridge: false` and runs only from a key in a compose window, in the chrome runtime. An `act` frame (archive, trash, move) sits behind its own default-off `bridge_allow_actions` setting and moves nothing until the person presses `y` on a prompt in the Thunderbird window. It runs the key handlers, so `u` reverses it, and trash never deletes for good. Every command states `bridge`. It is true only for a command that moves the view or the selection and does no harm doing so (`motion.*`). In v1 the bridge still refuses the chrome and message-pane commands, `motion.*` among them, because the background has no verb to start them. It is false for anything that changes mail, sends, discloses data or is hard to undo (`msg.*`).
- Phase 2 scope: `step.*` is deferred, and the typed-value commands listed in build order 2 get default keys with the phase 3 command line. The keymap matches a chord only when it binds that chord. The alt chords (`<A-h>`, `<A-l>`) stay out of phase 2, because the motions that use them are out of it.
- `downloads` is a required permission, for the same reason: an add-on with an Experiment cannot use optional permissions. Only `msg.save_attachments` uses it.
- `nativeMessaging` is a required permission, because an add-on with an Experiment cannot use optional permissions. The host itself stays optional. A command that needs it refuses with a message when it is missing.
- Hand checks go through `tools/owner_test/`: a visible Betterbird or Thunderbird with the worktree's build in a throwaway profile under `$XDG_CACHE_HOME/desertbird/owner-test/`. It never reads or writes a real profile. Its departures from the DesertFox tool are in [`tools/owner_test/README.md`](../tools/owner_test/README.md).

## Store rules

The rules of addons.thunderbird.net shape the build:

- An add-on with an Experiment gets a manual review, so the split table stays the evidence that the Experiment does only what no standard API does.
- Third-party libraries (`marked`, `turndown`) ship as the exact release files in a vendor folder, listed in `VENDOR.md` or `package.json`. They load beside the esbuild bundle and never go into it, so the store can match them against the release.
- A build that bundles our own code needs a source archive with build instructions and a lockfile, and `npm ci` must work.
- The Experiment bundle stays unminified, so the reviewer reads what ships. It is built with esbuild because the chrome runtime reuses the core key matcher.

## Keys on a page of another process

DesertFox takes plain keys on web pages through a content script and has none on `about:` pages. A remote page in Thunderbird is out of reach of the chrome runtime, and the setups that load key files into the main window passed plain keys aimed at a `browser` untouched, so only chords ran there.

Departure, step 1: when a tab comes to the front, its browser is remote and the focus sits on the window body or the tab strip, the overlay Experiment (`src/chrome/page_focus.ts`) focuses that browser after a tick. The page's own script then runs `j` and `q` on the options and help pages with no click. Any other focused element stays. The code lives in the overlay bundle because the key runtime has no size to spare.

Step 2, the page actor: a `JSWindowActor` named `DesertBirdPage` gives web pages and other add-ons' pages (`moz-extension:`) in a tab of the main window the page tree, the typing keys and insert mode. Its child (`src/chrome/page_actor_child.ts`, shipped as `experiment/page_actor_child.sys.mjs`) runs in the page's process. Its parent (`src/chrome/page_actor_parent.ts`) registers it from `pages.js` at the first `pages.install` and hands each key to the page runtime, which runs it with the same matcher as a key of any other tab. How it works:

- The child reads the key and one bit, whether the focus sits in a text field, and nothing else of the page. It takes a key only where the parent's matcher would: the parent pushes a skeleton of each tree (the tokens and the branches, no commands), and the child walks the page skeleton outside a field as the matcher does, with a count, a prefix, a capture branch and Backspace. It cancels such a key before the page's own listeners and sends it. Inside a field or in insert mode it takes only the root keys of the typing skeleton. A key off the skeleton inside a prefix or a count goes to the parent uncancelled, so the parent ends the sequence and its key list, and the page gets the key too. Any other key stays the page's and is never sent. Escape stays the page's too: the child sends it once the page's handlers ran, with whether one of them used it, and the parent leaves the field or insert mode only when none did.
- The parent pushes the skeletons on each keymap install and the insert flag on each change, and answers a child's hello with both. A child says hello when it is made (at `DOMContentLoaded`, or by the first push) and again when its page comes back from the back-forward cache. Until the answer comes the child takes no key. The start reaches the pages already open, so a page loaded before the actor need not wait for a key.
- Insert mode drops every plain key in the child at once. The skeleton marks the leaves that enter or leave insert mode (`i`, Escape, Ctrl+[), and the child follows them itself as it takes the key, so a fast key after `i` or Escape meets the new mode before the parent's push arrives. The push then confirms it. Insert mode also ends when the front tab's page is replaced (a new child says hello), so a new page starts in normal mode as in DesertFox.
- The chrome leaves every key of a page alone while that page's child is on and the focus sits in its top-level document (`Services.focus.focusedContentBrowsingContext`). Otherwise the old rule holds: only the close chord runs. That covers a frame of another origin, a same-origin frame (the child runs in the top-level document only, `allFrames: false`, and a key in a frame never reaches it) and the pages the actor does not match.
- Pages covered: `http`, `https`, `file` and `moz-extension` documents in the `web`, `webIsolated`, `webCOOP+COEP`, `file` and `extension` processes, top level only. The add-on's own pages (options, help, the overlay's pages) and any browser outside the tab panels (another add-on's popup) get an off answer. `about:` pages, message documents and compose stay as they were. `allFrames` stays false, because true would run the child in the `http` frames of a message pane.
- The modules load from a `resource://` root that `pages.js` names afresh on each load (`desertbird-actor-<time>`). The module cache keys on the URL, so a reloaded add-on under the old name would keep running the old child. `stop` turns every child off, unregisters the actor, drops the root and drops the callbacks into the add-on's scope, which dies on shutdown. An old module stays in memory until the app restarts.

Departures from DesertFox, which runs the whole key runtime, its modes and its matcher in a content script per page:

- The child sends a key and one bit. The matcher, the modes and the commands stay in the parent, so every tab has one matcher, no `<all_urls>` permission is needed and the child stays small.
- DesertFox keeps the mode per page and frame. Here the insert flag is per window in the parent, and the child holds a pushed copy.
- No per-site rules (`editable_add`, `editable_remove`, site modes). A page that draws its own editor needs `i`.
- The field check follows DesertFox `takes_typing` and its shadow walk, plus `select` and design mode. Any other divergence is a bug.
- DesertFox passes unbound keys to the page, except `/` and `'`. Here a key the matcher would not take at its position passes, the same rule.

Departure from the old setups that loaded a key file into the main window: their stop rule skipped plain keys whose target was a text tag or a `browser` element, so web pages were opaque and plain keys never ran there, while chords ran even in a field. The actor reads the field, so plain keys run on web pages and chords follow the field too.

Security: privileged code now runs in content processes. The child reads a key and a field bit, sends only those, and takes no message that names code: the parent sends a state (booleans and token lists), a scroll id from the fixed table of `page_actions.ts` with a count, a blur, or a hint pick (two colors and an action from a fixed set). The parent rebuilds each key field by field before the runtime sees it.

### Hints on a page of another process

`f`, `; f`, `; c` and `; y` label the controls of a web page or another add-on's page in a tab, top-level document only. The parent cannot read such a page, so the page actor's child does the work in the page's process:

- `hints.pick` in `hints.js` finds the front tab's actor through its browser (`getExistingActor`), focuses the browser so the child reads the label keys, and sends `DesertBird:Hints` with the colors of the scheme Thunderbird shows and the action. The child answers with the count of labels, and that count is all of the page that goes to the parent. A query that fails (the tab closed, the page went) counts as no labels.
- The child loads `src/chrome/page_hints_child.ts` (shipped as `experiment/page_hints_child.sys.mjs`) on the first pick in its process, so the key reader of every page stays small. It finds the targets with the selector of the page tabs and the same on-screen check, and runs the same pick as the chrome (`hint_pick.ts`): labels in a closed shadow root, narrowing on typed letters, then a script `click()`, a focus or a copy. The click comes from privileged code, so the page sees a trusted event.
- While the labels show, the child hands every keydown to the pick before the page sees it, also in insert mode and in a text field, and sends none to the parent. A key no label starts and Escape end the labels and are cancelled too.
- `; y` copies in the page's process through `nsIClipboardHelper`, which hands the text to the parent's clipboard itself, so the text never goes through the actor.
- The labels end on a pick, a key, a scroll, a click and `pagehide` (a navigation, or the page going into the back-forward cache), all seen in the child. A tab change, a window blur and a shutdown happen in the parent, and each already pushes the state to the children of the window, so the child ends the labels on any state push. A second pick ends the first, in any page of the process, because the pick module keeps one pick per process.

Departures from DesertFox, which scans, draws and reads keys in its content script and lets the background hand out labels across frames:

- Top-level documents only. Frames of another origin would need `allFrames` and a label set shared across children.
- The visibility check is the shorter `is_on_screen` of the page tabs. There is no text mode and no rapid mode.
- The hold of the page keys after `f` (1.5 s) still swallows a bound plain key typed in that time, so a second `f` right after a pick does nothing. An unbound key typed before the labels show reaches the page.

## Keys in the other tabs

DesertFox has one content script per web page. Thunderbird draws its tabs (calendar, tasks, settings, the address book, `about:` pages, search results, chat) in chrome documents and parent-process pages that no content script reaches. The `pages` Experiment (`experiment/pages.js`, `src/chrome/page_runtime.ts`) takes their keys. Departures from DesertFox, each with its reason:

- The page keys run in a bundle of their own on the window root, where DesertFox has one `content.js`. The size guard of `keys.js` was full, and the admission rule keeps this code out of it. `hints.js` is the precedent for a bundle that listens on the window root. It sees a key before the key runtime and steps aside in the mail tab, except for a key typed in one of its text fields (the typing keys), which this bundle takes and stops, so the two never take the same key.
- A decision by focus (`src/chrome/readable_focus.ts`) where DesertFox has no decision. A tab is readable when its document is a chrome document or a parent-process document. It is out of reach when the focus chain ends in a browser whose document the walk cannot enter, or when nothing in the tab has the focus and the front tab's browser is remote. The page actor runs the keys of such a page (see "Keys on a page of another process"). Where it does not, only the close chord runs, because the chrome cannot see a text field inside such a page. A text field or an open menu passes every key.
- The scroll target is the nearest scrollable ancestor of the focused element, else the scrolling element of its document, else, when that does not scroll, the largest visible scrollable element of the document, or of the front tab's panel in the window document (the settings tab scrolls inside a pane the focused sidebar button is not part of). DesertFox adds a site selector and always scans for the largest box. The chrome documents are known and there are no site rules here, and the scan runs only when the root does not scroll.
- `h` and `l` scroll 50 pixels sideways and `<C-f>` and `<C-b>` a page (the height of the target), as in DesertFox. A sideways key looks for a target that overflows in width, and a page tab and a message tab take them. `<C-f>` is Find in Thunderbird, so it stops being Find in these tabs only. The keys sit in the shared message tree, so they also apply in the message pane of the mail tab and in message windows, where `<C-f>` pages down as in DesertFox. In the thread list of the mail tab `h` and `l` stay the thread fold keys, since the list layer comes first.
- No smooth scroll. A web page that draws its own editor needs `i`.
- Typing in a field (`src/chrome/page_runtime.ts`, `typing_keys` of the command groups, the `typing_tree` of the keymap record). Departures from DesertFox, each with its reason:
    - Escape leaves the field only when Thunderbird did not use it. A second listener on the same target in the bubble phase blurs the field when the event is not `defaultPrevented`. DesertFox's `mode.escape` always runs. Here the quick filter clears on its first Escape and an inline edit in the address book cancels, and neither may lose its focus to a blur that runs first.
    - There is no `<A-Escape>` that sends Escape on to the page, since Escape reaches Thunderbird before this code.
    - Manual insert (`i`) is a flag per window in memory, cleared on Escape, a tab change, a window blur or a closed window. DesertFox keeps insert per tab and has the background enter it again when the tab returns. While it is on, plain keys go to the page, as in a text field.
    - A text field is read from the focus chain at each key (situation `field`), not set as a mode by a focus handler. A message body that runs the body script and the overlay's browser are not a field here: the body script has its own `<A-j>`, and the overlay has its own keys.
    - `mode.escape` here clears the flag and blurs the focused element. DesertFox's also ends find highlights, hint hover, site mode and fullscreen, which this runtime lacks.
    - `<A-j>` and `<A-k>` switch tab in a field through a keymap layer (`typing_keys`) cut by the `typing` need, so user bindings and help follow. DesertFox binds them in a `browser` section for the whole Firefox UI. Only one-key bindings of the commands the layer names join it from the user's keymap, because plain keys are text in a field.
    - The mail tab's text fields (quick filter, search box) take the same layer, run by `pages.js`. The key bundle (`keys.js`) did not have the 512 bytes it would need, and a second copy of the matcher feed there would cost more than reading the focus here. Insert mode itself (`i`) is bound in page tabs only, where the list keys do not own plain keys.
    - The status bar label shows insert mode for the flag. A page tab reports it through the same `mode` event as visual mode (`insert`), where DesertFox draws an in-page badge.
    - There is no `escape_to_page` site rule.
- The hold after a command that opens the overlay and the end report of the key list are copies of the mail runtime's, because the two bundles share no state.
- A key the page keymap leaves unbound passes to Thunderbird. DesertFox cancels unbound keys in some modes.
- The page keys are not a table of their own. Each command names what a tab must offer in `needs` (`list`, `message`, `body`, `tab`, `page`, `typing`, `close`, `pane`, `main`, beside the Experiment verbs), and `src/background/commands/tab_keymaps.ts` cuts the one keymap for each tab kind: a tab gets the keys of the commands it can serve, and the rest reach Thunderbird. DesertFox has the same field with other values (`content` and permission names). `needs` stays a string list, so the vendored type carries them. The reading keys a tab with no body script scrolls with are `page_keys` in the `page` group. A user binding goes into every tree its command allows, and `tab.close_mail` needs the list, so Ctrl+C and Ctrl+X still copy and cut.
- `J`, `K`, `<A-j>`, `<A-k>` and the `t` group (+Tabs) switch tabs in these tabs, `T`, `, h`, `, s`, `, ?` and `c` work there, and `g p a`, `g p t` and `g p c` open the add-ons, themes and config pages. Ctrl+J (Saved Files) and Ctrl+K (quick search) are Thunderbird's own, since DesertBird binds neither.
- Message mode: a message window is a tab kind of its own (`window`), with a tree of its own (`window_tree` in the keymap record). It offers `message`, `line`, `body`, `close` and `main`, and not `tab` or `pane`, so it takes the reading keys, the hint picks, the mail actions on the shown message, the command line (`:`, `/`, `m t`, `m m`, `m c`), `q`, and the `main` keys: zoom on the window, and new message (`c`), help (`g ?`, `, h`, `, ?`), options (`, s`) and the Thunderbird pages (`g p a`, `g p t`, `g p c`), which open in the first main window and bring it to the front (`main_window_of` in `handlers/tabs.ts`; with no main window open they refuse with a message). The tab keys (`t 0`) and the pane keys stay unbound there. `J` and `K` step to the next and previous message of the list the window was opened from, and `] u` and `[ u` to the next and previous unread one (`step.message`, keys of the `window_keys` layer, which only a message window takes, so the mail tab keeps `J` and `K` for tabs). The step shows the new message in the same window: its message id changes, so the hint labels and the find of the old message end. The command asks the view for a next or previous row first and refuses with a toast when there is none, so it never wraps (`] u` would wrap in Thunderbird). A window with no list, opened from an .eml file, refuses too. A count is ignored. `/`, `n` and `N` work in the body, because `find` and `n` and `N` need `line`, which the window offers: the line opens on `find ` and the body script finds in the message. From the header they do nothing, as in a message tab. The line in a message window lists and runs only the commands the window offers: its session carries the kind `window`, and `offered_in` (`commands/tab_keymaps.ts`) keeps a command whose needs the kind offers (`sort`, `open` and `tab` are refused with a message in the line). The overlay host finds a message window as it finds a main window (`open_overlay_windows`), and the line there closes on Escape with the focus back where it was: the focus capture takes the `messagepane` browser or the header element, so no fallback focus is needed (see "The command line in a message window" in `docs/thunderbird-behavior.md`). The one tree runs in the body and in the header. The body script starts on the message tree and asks the background with `body.tree` which tree it runs, because only the background can tell a message window from a tab (`windows.get` type `messageDisplay`). It switches to the window tree on that answer. A background that is still starting cannot answer, so the question repeats each second for 30 s. The `pages` bundle hooks `messageWindow.xhtml` too, and a window with no tabmail passes for a message tab whose browser is `messageBrowser`, read at key time because `about:message` may load after the hook, so `situation_of`, the message id (`gMessage`) and the scroll of `#messagepane` work as in a message tab. The header picks go to the background as `hint.window`, as in a message tab. A plain key the tree leaves unbound is swallowed in the header and the body, so Thunderbird's single keys (`j` marks junk) cannot fire. No mode label draws there, and the which-key panel and the toasts do not show there, because the hud page mounts in main windows only: the hud drops the `pending` and `mode` events of a window it does not track. The message tab keeps the message tree.
- A message tab with the focus outside the body (in the header or on the tab strip) takes the message tree, so `d`, `a`, `r` and the reading keys work there, run on the message the tab shows. Find in the message does nothing there, because it needs the body script. `page_message_tree` turns each `hint.pick` step of that tree, a user key's too, into a background `hint.window` step with the same action, so `f`, `; f`, `; c` and `; y` label the header and the body there as from the body (see "Hints in a message"). A plain key with no binding is cancelled in that tab, so Thunderbird's single keys such as `j` (junk) cannot fire. The body script keeps the keys while the body has the focus.
- `j` and `k` scroll a focused list that has its own selection (the address book's books and cards) and do not move its selection.
- `f`, `; f`, `; c` and `; y` label the front tab with `hint.window`, which needs `page`, a tab with no body script, so the message documents and the own pages keep `hint.pick`. The targets are the controls of the window and of the tab's own page when the parent can read it (settings, the address book, `about:` pages). The selector starts from DesertFox's clickable one (links, buttons, fields, `summary` and the click roles) and adds the XUL controls of Thunderbird's pages (`checkbox`, `radio`, `menulist`, `richlistitem`, `search-textbox`, `[role=treeitem]`). It leaves out these DesertFox selectors: `[tabindex]`, which in a chrome document marks whole panes and lists; `[onclick]` and `label[for]`, which sit on wrappers and labels whose own control already gets a label; `[role=menuitemcheckbox]` and `[role=menuitemradio]`, which live in closed menus. Any `contenteditable` but `false` counts as an editor (the bare attribute, `true` and `plaintext-only`), and a pick focuses it. A web page or another add-on's page gets its labels from the page actor (see "Hints on a page of another process"). A remote page the actor leaves alone (the add-on's own pages) gets the window's controls only, because its document is out of reach of the chrome. The scan of a page tab and of a web page also enters shadow roots, open and closed, because `moz-*` controls (the Add-ons Manager's side panel, menu openers and search field) keep their real button or field there. A host is dropped only when its shadow gives a visible target, so one control gets one label. A field host keeps its label (a date input can get two, one for the field and one for its calendar button), except `search-textbox`. A slotted replacement yanks its host's text. The on-screen check descends through the roots and follows the flat tree. The mail tab keeps its flat scan: its documents are large and its quick filter stays unlabeled.
- The pick and the page keys both listen on the window root, and the page keys were there first, so they would see a hint letter before the labels do once the hold after `f` runs out. The pick sets `data-desertbird-hints` on the window's root element while the labels show, and the page keys pass every key while it is set. A marker and not a call, because the two bundles share no state, as with the body script's marker. When the labels end, by a pick or a cancel, the pick also adds one to the `data-desertbird-hints-done` attribute of the same element and never removes it. `keys.js` and `pages.js` read it when an `f` hold begins and drop the hold at the next key if it changed, so a second `f` right after a pick labels again. The `:` hold never reads it.
- The key list (`g ?`, `, ?`) and the panel of a half-typed prefix show the keys of the tab: the page tree, or the message tree in a message tab. Departure from DesertFox, which draws the panel from the one runtime of the page: the chrome names the tree in the `pending` event (`source`, and `root` for `g ?`), because it knows the tab kind and the window and the background cannot tell which tree the front tab runs. Departure: `:help.whichkey` typed in the command line in a page tab still draws the mail tree, because the background command takes no tab and the command line is not the front tab's key runtime.

## Build order

0. Measure on the target Thunderbird ESR and on Betterbird, and write `thunderbird-behavior.md`. Capture plain keys in `about:3pane` from the Experiment, and cancel Thunderbird's own single-key shortcuts (`a`, `j`, `f` and others) in normal mode. Take keys in the message pane through `messageDisplayScripts`. Mount an extension page overlay in the chrome window. Time the round trip from the chrome runtime to the background and back. Check that each standard row in the table exists on the target ESR. Find the native host manifest folders for Thunderbird and Betterbird, which are unverified. Check that Betterbird is at 153.2.0 or later for `filter.set` and `search.threads`. Check that `tabs.create` works from a compose window, for `help.open`. This phase needs no shared core.
1. Pin the shared core in `vendor/desertfox/` with `tools/vendor_desertfox.sh`. Then set up the skeleton: the manifest, the Experiment with `keys.*` and `view.*`, and the registry with the motions and message actions.
2. Port the standard commands, group by group, in table order. `step.*` is not part of this phase: it waits for the later Experiment rows piece (`view.rows`), which also serves `motion.left`, `motion.right` and `step.thread_root`. Commands that need a typed or picked value (`msg.tag`, `msg.move`, `folder.open` with `o`, `tab.switch`, `filter.set` with a tag, `search.threads` and `sort.set`) ship their handlers and validators in this phase. Their default keys arrive with the command line in phase 3.
3. Command line, which-key and hints.
4. Compose: insert and normal mode, and the external editor through the host. Built: every compose window opens in insert mode. Escape makes normal mode, which stays until `i`, across focus changes and a draft save, and `<C-e>` edits in either mode. The mode covers the body and the address and subject fields, and the chrome runtime (`composewin`) runs it. Normal mode and the label do not depend on the `external_editor` setting, which gates only whether `e` and `<C-e>` open the editor. See Compose normal mode. HTML compose converts in both directions in the add-on, in the background page. Only the part the user wrote converts. That part is the top-level nodes that are not stop nodes (`moz-cite-prefix`, `blockquote[type=cite]`, `moz-signature`, `moz-forward-container`). They sit above the quote in a top-posted reply and below it in a bottom-posted reply, which is the Thunderbird default. The edited text goes back in the same place. A reply with user text on both sides of the quote is refused with a message. `turndown` turns that part into Markdown for `editor_start`. `marked` turns the edited Markdown back into HTML. The quote and signature nodes go back untouched, so cite quoting and tables survive. Both directions escape HTML, so tag text in a quoted message never becomes a live tag. `setComposeDetails` runs only when the Markdown changed. Parse with `DOMParser` and never set `innerHTML`. Test the round trip on top-posted, bottom-posted, forwarded and no-quote replies. Built in `src/background/compose_markdown.ts`. With nothing written yet, the text replaces the blank line Thunderbird put the cursor on: the first node after the quote in a bottom-posted reply, else the first node of the first blank run. The HTML from `marked` is rebuilt node by node from an allowlist of elements and attributes, with links limited to `http`, `https` and `mailto` and images to `http`, `https` and raster `data:` URLs, so Markdown the user writes cannot add a script, an event handler or a stop node. The libraries load before `background.js` from the manifest, so they cost the startup of the background page about 80 KB of script even with the editor off.
5. Migration notes for users who load key files through an autoconfig file.
6. Listing on addons.thunderbird.net, with the Experiment code open to a by-hand review.

### Backspace in an open which-key

Backspace drops the last key of a half-typed sequence, as in DesertFox (`key_flow.ts`: reset, type the kept keys again, report the shorter prefix, cancel the key). Departures:

- DesertFox does it in its key flow. DesertBird has three key flows (chrome runtime, message body script, own pages), so the step is in `matcher_for_tree` (`src/shared/keymap_tree.ts`), a wrapper around the pinned matcher. The vendored matcher is not edited.
- The wrapper keeps the last pending result and takes `keys` from it, as DesertFox does. It needs no list of its own.
- It answers with the pending result of the shorter prefix (an empty one when no key is left) and adds no `back` result kind. Callers already cancel a pending key and report its prefix, so no caller changes, which saves the bytes that a `back` branch in each caller costs in `keys.js`.
- Backspace with nothing pending is an ordinary key and goes to Thunderbird.

### App bundle

### Zoom bundle

The zoom keys run in the mail tab, message documents, own pages, the page tabs and the body of a compose window (window type `msgcompose`). Web pages and other add-ons' pages get them through the page actor. They start from DesertFox `src/commands/zoom.ts`: the same `zoom.by {delta}` and `zoom.set {level}` (`:zoom`), the same steps (`z i`, `z +`, `z o`, `z -` by 0.1, `z m`, `z r` by 0.5, `z =` to 1, `z I` to 3, `z O` to 0.3) and the same clamp to 0.3 .. 5. Departures, each with its reason:

- An Experiment where DesertFox calls `tabs.getZoom` and `tabs.setZoom`. Thunderbird has neither (measured), and the message pane of the mail tab is no tab.
- `z M` and `z R` stay the thread folds of the mail tab, so the half step has the lower-case keys only.
- A count multiplies the step in one change (`3 z i` is +0.3), where DesertFox runs the command once per count. The result is the same, with one round trip.
- A step that the clamp would turn the other way does nothing: Thunderbird's own Ctrl+minus reaches 20%, below the floor, where `z o` would zoom in. Firefox stops at 30%, so DesertFox never meets it.
- No zoom memory per site. Thunderbird keeps the zoom on the browser: the message pane keeps it across messages and folders, and a new message tab or window starts at 100%.

### Compose normal mode

A compose window has one mode, shared by the body and the text fields of its header: the address inputs (To, Cc, Bcc and the others), an address pill being edited and the subject. The chrome runtime owns it (`experiment/composewin.js`, `src/chrome/compose_runtime.ts`). It listens on `window.windowRoot`, which sees a key before Thunderbird's handlers and before the compose script in the body (measured, see [`thunderbird-behavior.md`](thunderbird-behavior.md), Compose window keys). Each window opens in insert mode, and its mode then changes only on Escape and `i`, never on focus or blur, because a draft save moves the focus. Each window has its own mode. The mode lives in memory only, an exception listed in `AGENTS.md`.

- Escape in insert mode enters normal mode and is cancelled. Escape with the autocomplete popup of an address input open passes, so the popup closes, and the next Escape enters normal mode. The popup state comes from the focused input (`popupOpen`, `popup.state`), because `#PopupAutoComplete` reads closed while the list shows. Escape in a pill being edited passes too, so the pill goes back to its address. Escape in normal mode passes, so Thunderbird still closes the find bar or a notification with it, and ends a half-typed sequence.
- In normal mode `i` returns to insert. A character key, Space, Enter, Backspace and Delete never reach the draft or a field, bound or not. In the body Tab and Shift+Tab are held back too, since Tab inserts a tab in a plain-text body. In a field they pass, so a typed address still becomes a pill and the focus moves on. The arrows, the function keys (F6) and every chord the tree does not bind pass (Ctrl+Enter, Ctrl+S, but also Ctrl+V, Ctrl+Z and the Paste and Cut keys, which edit). A chord the tree binds runs. A chord with Shift on a letter matches the lower-case letter, as Thunderbird reports it (`<C-S-t>`).
- Keys elsewhere in the window (From, the attachment list, the contacts sidebar, the find bar) all pass, in either mode.
- Known limits: a mouse paste, a drag, the context menu and the first key of an IME composition (`Process`) can still change the draft in normal mode. A key of an IME composition is never touched. A user binding on `i` or on Escape has no effect, since those keys are fixed. A held key runs once.

The keys are a tab kind of their own, `compose`, with a tree of its own (`compose_tree` in the keymap record), which the background installs with `composewin.install`. Only `COMPOSE_COMMANDS` can run from it, by default or by a user key: `compose.edit_external` (`e`), `compose.save` (`s`), `help.open` (`?`), the zoom keys, the field jumps `compose.focus` (`g t` To, `g c` Cc, `g b` Bcc, `g s` Subject, `g m` body; Cc and Bcc show their hidden row), `compose.close` (`q`) and `compose.send` (`g S`). The last three run in the chrome runtime from its fixed table, and the others leave through `composewin.onInvocation` to the router. A sequence of the tree (`z i`, `g t`) works with a pending key. No hud shows in a compose window, so a pending key draws no which-key.

- `q` runs Thunderbird's own `cmd_close`, so a changed draft shows Thunderbird's prompt with Save, Cancel and Discard changes, and an unchanged one closes at once. `windows.remove` and `window.close()` would drop a changed draft with no prompt (measured). The prompt waits in a nested event loop, so the runtime runs the command from a timer and the key handler returns first.
- `g S` runs `cmd_sendWithCheck`, the command of Ctrl+Enter, from a timer as well. Thunderbird's checks and its send confirm (`mail.warn_on_send_accel_key`) apply. The `compose_send` setting gates it and is off by default: while it is off the key is held back and runs nothing.
- The mode label is a `span` in the window's `#status-bar`, after the language, with `-- INSERT --` or `-- NORMAL --`. It is chrome, so it never reaches a draft, and it shows whatever has the focus. The window listener draws it when the window is hooked and removes it on unload and on shutdown.
- Lifecycle: the first `composewin.install` registers one `ExtensionSupport` window listener for `messengercompose.xhtml` and hooks the compose windows already open. A later install replaces the tree and the send flag and adds no listener. `shutdown` (the add-on disabled, removed or updated) removes the key listener and the label of every compose window and the window listener. An install after that (enabled again, or the new version) hooks the open windows again in insert mode.
- Tested on Betterbird only. Thunderbird compose is not measured for this feature.

### Compose window bundle

`experiment/composewin.js` is the Experiment API `composewin`, the key runtime of the compose windows. It decides what happens to every key of a compose window, so it is chrome runtime code under the admission rule, and it has a bundle of its own because `keys.js` and `pages.js` have no room. It walks the compose tree itself and bundles neither the vendored matcher nor the key token reader. Its ceiling is 8192 bytes. ## Risks

- An Experiment breaks when Thunderbird internals change between ESR releases. The fixed verb table keeps the breakage in one small file, and the key tests catch it.
- addons.thunderbird.net reviews Experiment code by hand, and the review can be slow. The no-eval rule removes the main ground for a refusal.
- Betterbird patches the thread pane (for example its multi-line view). `view.rows` needs a test on both apps.
- Thunderbird has single-key shortcuts of its own. A key the chrome runtime does not cancel runs both actions.
- If the round trip from chrome to background is slow, held `j` lags. That is why the motions run in the chrome runtime.

## Phase 0 findings

Phase 0 ran on Thunderbird 153.7.0 ESR and Betterbird 153.7.0, with the same result on both. The numbers and the method are in [`thunderbird-behavior.md`](thunderbird-behavior.md). The design decisions above stand. Where a measured fact differs from the text, the text carries a note and the fact is listed here.

- Overlay mount: the overlay is a remote `browser` element that the Experiment creates in a chrome document, in the main window or inside `about:3pane`. It loads the extension page with the extension APIs and takes keys. An extension-page iframe in `about:3pane` never loads. The chrome runtime must skip keys that the overlay has focus for.
- `step.unread` across folders: `messages.query({unread: true})` over all folders takes about 1.1 s on 5,000 messages, so it does not run per key. The command reads the unread counts with `folders.getFolderInfo` (about 21 ms for 50 folders), picks the next folder with unread mail, then queries that one folder for one result (`messagesPerPage: 1`). In the shown folder it reads `app.viewRows`, which needs no query and follows the sort. It stays in the background. The timings on a folder of 10,000 messages are in [`thunderbird-behavior.md`](thunderbird-behavior.md), Step keys and visual mode.
- Collapsed threads: `mailTabs.setSelectedMessages` on a message inside a collapsed thread selects it and opens the thread.
- `tabs.remove` on the primary mail tab is a no-op, also when it is the only tab. `tab.close` does not call it there: it moves the focus to the thread list, so `q` leaves a message in the reading pane. In a message window it removes the window.
- Mail keys in a message: the reading pane, a message tab and a message window run the mail keys of the message groups (`messages`, `compose`, `clipboard`, `followup`, `snooze`, `tabs`, `cmdline`) on the displayed message, through the body script and `body.invoke`. Keys that need the thread list or the mail tab stay out. A message window runs message mode, without the tab and pane keys (see Message mode).
- `messages.tags.list` needs the `messagesTagsList` permission. `commands`, `menus` and `addressBooks` calls need their own permission or key too. There is no `messenger.clipboard`.
- Plain keys: a capture listener on the top window sees plain keys in the thread list, the message pane, a message tab and a message window, and cancels each Thunderbird single-key shortcut that acts there. In all four contexts that covers `m`, `s`, `j` and `a`. On the thread list only, `f`, `b`, `n`, `p`, `1` and `Enter` were measured and cancelled. `r` and `R` do nothing by default in any context. Chords were measured, see "Cancelling Thunderbird's chords" in [`thunderbird-behavior.md`](thunderbird-behavior.md). Key repeat and other tab types were not measured, see "Not measured" there. The first press after a focus change can be lost.
- Message pane: for local mail the message body browser is not remote, so a chrome listener sees its keys. This differs from the Architecture row for `messageDisplayScripts`. The decision stands until feed, IMAP and remote content are measured.
- Hints in a message: `f`, `; f`, `; c` and `; y` with the focus in a message body, in the reading pane, a message tab or a message window, label the message header and the body as one set. The body script's `hint.pick` sends `body.hints` with the action. The background checks the action against the command's params with `check_args`, takes the window and the tab from the sender and calls `hints.pick` with `place: "message"`. The parent follows the focus chain to `#messagepane`, whose document is `about:message` in each of them, and labels in this order: the header controls of `about:message` (the toolbar buttons, More, the star, one label per address pill, the day/night switch, the tags, the attachment bar and each attachment of an open list), then the links, buttons and fields of the body. A split button (Reply All, Reply List) gets one label, on its main part, so a pick runs the main action. More and the other menu buttons open their menu, where the user goes on with the arrows and Enter. A pill opens its address menu, a tag takes the focus (`; y` copies its name, and a pill's yank copies its address), and an attachment is selected in its list, which takes the focus, so Enter opens it. A body link or button is focused, and a trusted Enter follows from a timer, after the picking key, and only when the focus still sits on that same element, so Thunderbird's check for a link that lies about its address runs as before. The parent answers with the count. It answers 0 when the focus has left the body or another tab is in front by the time the request arrives, and -1 when the body is remote (a feed shown as a web page). A message window has no tabs, so the tab check is skipped there. On -1 or a failure the body script labels the body alone, as before. The body drops plain keys from `f` until the answer, at most 1.5 s (the hold of the chrome runtime), so a key typed before the labels draw runs no command. The parent answers once its labels own the keys, so a key that reaches the body after the answer came after the labels. A scroll, a blur, a click, Escape or a keymap change in the body drops a pick whose answer is still out and keeps the hold, and a late -1 then draws nothing. The labels end on a pick, Escape, a key no label continues with, a scroll or a click in the main window, `about:message` or the body, a window blur that leaves the window without the focus, a tab change, another message loading (`MsgLoading`) and a shutdown, and a target that left its document is not acted on. `hints.pick` with no place in a message tab (the header keys, `:hint`) or a message window reads `#messagepane` from that `about:message` and labels the same set, or the header alone when the body is remote or not loaded. A stale `hint.window` from the header, after a switch to another tab, labels the tab in front, as in the page tabs. The body labels of the parent wear the theme colors of the window's labels. A pick on a check box or a radio button clicks it, in every hint scan of the parent.
- Round trip: a key reaches the background in under 1 ms, so the chrome runtime can send finished invocations to the background. The motions stay in the chrome runtime by decision. Held keys were not timed.
- Native host manifests: both apps read only `~/.mozilla/native-messaging-hosts/` in the user folders. The system folders were not tested.
- Two traps: `compose.beginReply` crashes the app when the account has no identity, and `mailTabs.update` with a displayed folder throws on the first display of a folder though the folder displays.
- Betterbird at 153.7.0 passes the `filter.set` and `search.threads` checks.

Phase 0 answered both former open questions:

- The overlay mounts as a remote `browser` element in a chrome document, not as an iframe of an extension page in `about:3pane` and not as a sized panel.
- `step.unread` across all folders uses the folder counts and one single-result query, so a key press stays under half a second on 50 folders and a folder of 10,000 messages. It stays in the background.

The e2e startup ready signal (`wait_startup` in `tools/e2e/harness.mjs`) starts from the DesertFox key test (`wait_takes_keys` in `test/key/harness.mjs`) and departs from it in these ways. DesertFox probes with an unbound key (`F4`) that the page reports to its server. DesertBird takes no test hook in `src/`, so no page reports a key. The probe is a bound key, `w m`, and the helper add-on reads its effect on the message pane. A bound key has an effect, so the probe restores the pane and waits until it has held its first value for 1.5 s with no press in flight, because a slow key can land after a later press. DesertFox has no state to restore. Each probe try waits 1500 ms for the flip, where DesertFox waits 200 ms (`KEY_PROBE_TRY_MS`). The flip comes from a poll of the helper, which costs more than a page report, and a shorter wait presses a second toggle before the first lands. The probe shares the one ceiling `E2E_STARTUP_MS` with the helper wait, where DesertFox has its own probe timeout. There is no retry count. Escape goes before `w m` so a lone `w` cannot pair with the next try. A start with no helper add-on keeps the fixed wait, because there is nothing to ask.
