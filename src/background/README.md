# Background

The persistent background page. It owns the command registry, compiles the default keymap, hands it to the Experiment and runs every command that lives on standard APIs.

## Files

- `commands/`: the command table, one file per group. `define.ts` holds the `CommandGroup` shape, which requires `bridge: boolean` on every command, and the `scoped` wrapper. `motion.ts` holds `motion.*`, which run in the chrome runtime and carry no handler. `clipboard.ts` holds `msg.yank` and `msg.open`. `tabs.ts` holds `tab.*`. `reading.ts` holds `message.scroll_down`, `message.scroll_up`, `message.half_page_down`, `message.half_page_up`, `message.page_down`, `message.page_up`, `message.scroll_left`, `message.scroll_right`, `message.top`, `message.bottom`, `message.find_next`, `message.find_prev` and `hint.pick`, which run in the body script (`runs_in: "message"`, no handler here) and bind through `message_keys`, a keymap of their own, and `search.message` (typed as `find`), which runs here. `message_keys` also binds `/` to `cmdline.open` with `find ` typed. `hints.ts` holds `hint.window` (typed as `hint`; `f` in the mail tab, handler `handlers/hint_window.ts`), which asks the `hints` Experiment to label the mail window (`; f`, `; c` and `; y` are the same command with `action` `focus`, `activate` and `yank`); the keys of the labels are the Experiment's own. `app.ts` holds `msg.undo` (`u`, `:undo`, handler in `handlers/undo.ts`), `thread.open_conversation` (`g C`), `app.open_page` (the `g p` pages), `pane.focus` (`g f`, `g e`, `g m` in the mail tab; `g f`, `g e`, `g m` in the message document, which also binds `u` and `g C`) and `pane.left`, `pane.right` (`H`, `<A-h>`, `w h` and `L`, `<A-l>`, `w l`, also in the message document), each but `msg.undo` a call of one chrome verb in `handlers/app.ts`. `thread.ts` also holds `view.half_page` (`<C-d>`, `<C-u>`, ten rows). `view.ts` holds `filter.set`, `filter.by`, `search.threads`, `sort.set` and `pane.toggle`. The `list` and `date` fields of `filter.by` (`F m l`, `F m d`) go through the `filter` Experiment. `menu.ts` holds `menu.down`, `menu.up`, `menu.left` and `menu.right` (`j`, `k`, `h` and `l` in `menu_keys`, the key table of the `menukeys` Experiment, which `menu_key_table` in `tab_keymaps.ts` builds with the user's single-character keys on top; they run in the chrome and carry no handler). `context.ts` holds `context.menu` (`, m` in every tab kind, message windows and compose normal mode; handler `handlers/context.ts`, one call of the `context` Experiment verb `open`, which does nothing when the focus has no target). `zoom.ts` holds `zoom.by` and `zoom.set` (`:zoom`; `z i`, `z +`, `z o`, `z -`, `z m`, `z r`, `z =`, `z I`, `z O` in the mail tab, message documents, own pages and page tabs, not yet in web pages), which read and set the zoom of the message pane or the front tab's page through the `zoom` Experiment, and refuse where there is nothing to zoom. `unsubscribe.ts` holds `msg.unsubscribe` (`g u`, handler in `handlers/unsubscribe.ts`, pure header parser in `list_unsubscribe.ts`; the first press stores a pending record under `desertbird_unsubscribe_pending` and previews, the second within 15 seconds opens the https page or a mailto draft). `step.ts` holds `step.unread`, `step.starred` and `step.attachment`, which step the list, and `step.message` (`J`, `K`, `] u`, `[ u` in a message window only, through the `window_keys` layer; handler `step_message` in `handlers/app.ts`, which refuses outside a message window and calls `app.appCommand` with one of the four step names, which the Experiment answers false for at an end or with no list). `folders.ts` holds `folder.collapse` (no default key), `folder.open`, `mark.set`, `mark.jump`, `jump.back` and `jump.forward`. `messages.ts` holds the message state commands (`msg.archive`, `msg.delete`, `msg.read`, `folder.read_all`, `msg.flag`, `msg.junk`, `msg.tag`, `msg.move`, `msg.copy`) and `compose.ts` holds `msg.reply`, `msg.forward`, `msg.new`, `compose.edit_external` (`:edit`, see `external_editor.ts`) `compose.save`, and `compose.focus`, `compose.close` and `compose.send`, which the compose window runtime (`composewin`) runs in the chrome. The others all run here. A group lists its commands and the default normal-mode keys that run them. `captures.ts` moves each leaf that waits for a key press (`M`, `'`) under a capture branch after the compile. `index.ts` joins the groups into `registry`, `DEFAULT_KEYMAP` (the mail tab) and the compile functions (the default bindings through the vendored compiler). `tab_keymaps.ts` builds the other trees from the same table. Every mail sequence that the message tree lacks (`] a`, `; ;`) gets a leaf that runs nothing, so a list sequence never breaks partway and runs its tail as a message key. A prefix the message tree lacks also takes any one key. which-key hides these keys and opens no panel for a prefix that holds only them. `GROUP_NAMES` in `index.ts` names each prefix for which-key, and a binding carries its short which-key label as `label`, since help and completion read the command label. A new group is one file and one line in `GROUPS`.
- `external_editor.ts`: `compose.edit_external` (Ctrl+E in a compose body), behind the `external_editor` setting (default `false`), independent of `bridge`. `:edit` exists but refuses outside a compose window, and the command line does not open in compose windows yet, so today only Ctrl+E and `e` in compose normal mode reach it. It holds the one-shot client of the native host `desertbird_host` (`editor_start`, `editor_collect`) and the jobs, one per compose tab, under `desertbird_editor_jobs` in `storage.session`. The setting is read before every host call, so nothing reaches the host while it is off, a resumed job included. An HTML message goes to the editor as the Markdown of the user's text (`ext: "md"`, through `compose_markdown.ts`) and the job keeps that Markdown, so the write is skipped when the edit differs only in the closing newline. The result is written with `setComposeDetails` only when the text changed and the body still equals the one the editor started from. Otherwise a toast says why. A closed or sent compose window orphans the job with a toast that names the loss: its loop collects on until the editor ends and then discards the text. A failed send leaves the job alone. At each start `main.ts` calls `resume`: every job collects again, and the job of a gone tab is orphaned first. The add-on writes no file. The host owns the scratch file and removes it on the collect that ends a job. A job dropped without that collect (the setting turned off, three failed collects in a row) leaves its file until a later `editor_start`, a day or more on, sweeps it. A compose window has no hud, so its toasts show as desktop notifications. `create_compose_requests` answers the `compose.edit` request of the compose script and takes the window from the sender.
- `compose_markdown.ts`: the HTML side of the external editor. It parses the body with `DOMParser`, takes the top-level nodes outside the stop nodes (`moz-cite-prefix`, `blockquote[type=cite]`, `moz-signature`, `moz-forward-container`) as the user's text, refuses text on both sides of them, and turns that text into Markdown with `turndown`. Tables, underline and strike stay HTML in the Markdown. A bare web or mail address stays text, since the editor's own `Marked` instance does not link it. An image keeps an `http`, `https` or raster `data:` source, or a `mailbox:` or `imap:` source that the original body held on an image. Any other image is counted by `dropped_images`, and `external_editor.ts` names the loss in a toast after the write. On the way back `marked` makes HTML, which is rebuilt from an allowlist (no script, no `on*` attribute, links only `http`, `https` and `mailto`) and put where the user's text was. The stop nodes are never converted. `turndown` and `marked` are the vendored release files in `vendor/turndown/` and `vendor/marked/`, which the manifest loads before `background.js`. They reach this module as globals and never enter the bundle.
- `new_mail_notify.ts`: desktop notifications for new mail and the `notify.toggle` handler (`commands/new_mail.ts`). `main.ts` registers its listeners once at the top level. The notification id to message ids map is in memory. See `docs/thunderbird-behavior.md`.
- `config/`: the settings store and the user keymap, with the version key and migrations. See its README.
- `commands/page.ts` and `commands/tab_keymaps.ts`: the `page.*` reading commands (they run in the `pages` bundle of the chrome, from a fixed table, bound through `page_keys`) and the tree builder. Every command lists what a tab must offer in `needs`: `list` (the thread list), `message` (a shown message), `body` (the body script, which find and hints need), `tab` (a tab of the main window, with the tab bar and help), `line` (a window that can show the command line: a main window tab, an own page and a message window), `close` (a tab or message window that `q` closes), `pane` (the panes of the main window), `main` (a command a message window runs too: zoom acts on the key's window, and new message, help, options and the Thunderbird pages open in a main window, the first main window for a key in a message window, through `main_window_of` in `handlers/tabs.ts`) and `typing` (a tab that takes the keys of a text field and manual insert), `compose` (the body of a compose window) and `needing` in `define.ts` gives a group its default. `default_keymap_of` and `keymap_of` keep, for a tab kind (`message`, `window`, `own`, `page`, `compose`; `window` is a message window, message mode), the keys of the commands it can serve, taken from `message_keys`, `normal_keys` and `page_keys` in that order of priority (only a kind with a body takes `message_keys`). `cmdline.open` with typed text needs what the typed command needs, and `line` for the line itself. A user binding goes into every tree its command allows, and a `null` into all. `compile_tab_keymap` compiles one kind, and a kind with a body also ends the mail sequences it lacks in a leaf that runs nothing. `page_message_tree` cuts the find line from the message tree for a message tab with the focus outside the body, and turns each `hint.pick` step into a background `hint.window` step with the same action. `message_background_commands` lists the background commands a message key may run. `typing_keys` of a group are the chords that run in a text field (`<Escape>`, `<C-[>`, `<A-j>`, `<A-k>`), apart from the three layers above. `compile_typing_keymap` compiles them, and a user binding joins only as one key for a command the layer names. The kind `compose` (the body of a compose window) takes the `compose_keys` of the groups first and then only the commands of `COMPOSE_COMMANDS`, for a default or a user key alike, and offers `tab` (for `help.whichkey`) and no close. `main.ts` stores the trees in the keymap record (`message_tree`, `page_tree`, `own_tree`, `compose_tree`, `typing_tree`) and installs the page trees and the typing tree through `pages.install`.
- `cmdline/`: the command line's completion and sessions (see its README). `commands/cmdline.ts` holds `cmdline.open`, which stores the session and calls `overlay.mount`.
- `window_types.ts`: the `windows` API type string of a message window, shared by the handlers, `body_requests.ts` and `main.ts` (which tracks message windows in the hud).
- `body_requests.ts`: answers the `body.invoke` request of the body script. It also answers `body.hints`: it checks the action with `check_args` against the params of `hint.pick`, takes the window and the tab from the sender and asks the themed `hints.pick` for the message place, answering -1 when it cannot ask. It takes the window id and the tab from the sender, reads the displayed messages, and runs the command through the router. It accepts only the commands `message_background_commands()` lists (the background commands a message key binds). It answers `body.tree` with the tree of the sender's document: `window_tree` in a message window, else `message_tree`. A `body.invoke` from a compose window (window type `messageCompose`) runs only the ids of `COMPOSE_COMMANDS`, with no messages, and the message set never applies there.
- `popup_requests.ts`: answers the `popup.run` request of the toolbar popup (`src/popup/`). It accepts `options.open` and `help.open` only, from the popup page only (no tab, the page address of the popup), and runs them through the router in the last focused main window.
- `handlers/message_find.ts`: `search.message`. It sends `body.find` to the front tab of the window and refuses when no message is shown or the text is not in it.
- `bridge/`: the port to the native bridge host behind the `bridge` setting, the one path a command from outside takes, the reads, the `draft` frame and the confirmed `act` frame (see its README). `router.ts` exposes `route` for it, which throws instead of showing a toast.
- `hud/`: the which-key panel, the toasts and the mode label of the status bar (see its README). `notify.ts` sends refusals to its toasts.
- `main.ts`: stores the compiled keymap under `desertbird_compiled_keymap` with a hash of the effective bindings (defaults plus the user's) and the message keys. The record also holds `message_tree`, the keys of the message document, which the body script reads from storage and the Experiment never gets. It calls `keys.install` on every start and again when storage changes, and routes `keys.onInvocation` to the router.
- `scheduler.ts`: calls its `on_due` listeners at every background start and on a repeating alarm every minute. It keeps no due list: each feature reads its own store for what is due. Firefox alarms do not survive a restart, so `start` creates the alarm again each time. `main.ts` creates the instance, a feature adds its listener there and `start` runs last. A listener can run twice at once, so it must act once per item. A snooze due while Thunderbird is closed wakes at the next start.
- `snooze_store.ts`: the snoozed items under `desertbird_snoozed`, with a `record_version` and `migrate_snooze_record` as the migration hook. An item holds the Message-ID header, the origin account and the due time, never the numeric message id, which changes when the message moves. `wake_due` runs a wake on each due item and removes the item only after the wake succeeds, so a failed wake retries on the next tick. An item whose wake is still running is skipped.
- `snooze_presets.ts`: pure time math for the presets (`later_today`, `tomorrow`, `weekend`, `monday`) with the clock passed in.
- `followup_store.ts` and `followup_presets.ts`: the follow-up reminders under `desertbird_followups`, built like the snooze store (`record_version`, `migrate_followup_record`, an item holds the Message-ID header, the account, the anchor date and the due time). `fire_due` runs a fire on each due item and removes the item after it returns. A throw keeps the item for the next tick. A cancel or a new reminder that lands during the fire makes `still_wanted` false. The presets (`one_day`, `three_days`, `one_week`) are 24 hour multiples of now.
- `undo_log.ts`: the undo stack under `desertbird_undo`, as `{record_version, entries}` on the record store, with `migrate_undo_record` as the migration hook. One stack serves every window and keeps the newest 20 entries. An entry is a delete, archive or move (per message the Message-ID, the origin folder and the folders to search) or a read, star or junk change (per message the Message-ID, its folder and the old value) or a tag toggle (per message the Message-ID, its folder, the tag key and whether it had the tag). Version 2 of the record added the tag entry, and `migrate_undo_record` keeps version 1 entries. `record` holds the log for the whole mail change, so a `u` pressed during a `d d` waits for its entry. `undo_newest` runs undos one at a time in a queue of their own. Each takes the newest entry, waits for its copies without the log, then holds the log for the last lookup and the moves. So two quick `u` presses apply in stack order.
- `handlers/undo.ts`: records the entries and runs `u`. `msg.delete`, `msg.archive`, `msg.move`, `msg.read`, `msg.flag` and `msg.junk` call `record_moved` or `record_state`, and `msg.tag` calls `record_tag`, which take the log before their first await. `u` looks each message up by Message-ID in the destination only, matches copies that share a Message-ID by the recorded Date header and size, and retries a missing one on `retry_delays_ms`. Every lookup runs before any move. A missing message moves nothing on the first `u` and marks the entry. The next `u` moves back what it finds and drops the rest. Undo only moves a message back, or writes an old value back, and never deletes. A message with no Message-ID, and a delete from Trash, get no item and a warning toast. Snooze and `folder.read_all` are not recorded.
- `handlers/message_query.ts`: `query_all`, every page of one `messages.query`, shared by the follow-ups and the undo.
- `record_store.ts`: a versioned record in `storage.local` with a memory copy that drops on `storage.onChanged`. Reads and updates run one at a time, so two quick updates lose no write.
- `router.ts`: look up, `check_args`, check `needs`, call the handler on the message ids the invocation carries. Any failure ends in a notification.
- `notify.ts`: shows a refusal as a toast in the window it came from, with a system notification when no toast can show. A key never fails silently.
- `handlers/step.ts`: the step commands. They read the list through `app.viewRows`, in blocks of 500 rows, and select with `mailTabs.setSelectedMessages`. `step.unread` with `all_folders` picks the next folder with unread mail from the `folders.getFolderInfo` counts and one `messages.query` result, shows it and focuses its thread list.
- `handlers/zoom.ts`: `zoom.by` and `zoom.set`. They clamp the level to 0.3 .. 5, and a step that the clamp would turn the other way (a zoom out from Thunderbird's own 20%) does nothing. The steps of one window run one after the other, so two fast keys both count.
- `handlers/filter_terms.ts`: the List-Id and date terms of `filter.by` (`F m l`, `F m d`), which `mailTabs.setQuickFilter` cannot carry. With several messages selected it takes the cursor message (from `app.viewRows`), and it refuses a message with no List-Id. `selected_or_cursor_ids` gives every `filter.by` field the cursor message when nothing is selected. `filter_set_args` turns the terms into a `filter.set` call.
- `handlers/view.ts`: the view commands. They take a `ViewApi` subset, find the mail tab of the invocation's window and act on it. `sort.set` has the `s d`, `s j`, `s f`, `s z`, `s t`, `s a`, `s u` and `s o` keys, and the command line takes `sort --date --descending`. `filter.by` (`F m f`, `F m s`, `F m r`, `F m t`) adds a filter on the sender, subject or first recipient of the cursor message, or on the tags of every selected message, to the remembered filter. On a thread or a multi-selection a text field reads the cursor row while it is selected (the root of a closed thread), else the first selected message, and refuses nothing. A text field replaces the earlier text filter. The tag field replaces the tags and keeps the text. The list and date fields (`F m l`, `F m d`) are the `by_message` part of the remembered filter, which the `filter` Experiment applies. `apply_filter` sends it again after each `setQuickFilter` call, because that call clears it: after `F u`, `F s`, `F a`, `F t`, `:search`, every step of `/` and its Escape. `F r` drops it. When the Experiment refuses, the memory keeps the quick filter alone, which is what the tab then shows. The applies of a tab run one after the other. The recipient is the first To or Cc address that is none of the identities of the user. `search.threads` and the tag form of `filter.set` are reached by the `/` and `F t` keys, which open the command line with the command started.
- `handlers/tabs.ts`: next, previous, switch by number or title, go to a place (`tab.goto`, `t $`), the last used tab (`tab.alternate`, `t l`), move (`tab.move`, `t m` and `t M` open the command line with it typed) and close. `tab.alternate` reads `desertbird_last_tab_<window id>` in `storage.session`, which `main.ts` writes on each `tabs.onActivated` (the tab the window left), so no state lives in memory. The session store clears on an add-on reload or update and on an app restart, and `tl` refuses until the next switch. The keys stay after a window closes, a number of small records for the session. `tab.move` refuses the first tab, which stays first, and clamps a move to places 2 to last. They take `tabs` and the window id of the key press. `tab.next` and `tab.prev` take a count and make one switch to the tab that many steps away, wrapping. `tab.close` in a message window removes the window. On the first tab, the main mail tab, it moves the focus to the thread list with `app.paneFocus` and closes nothing: the tabs API marks that tab by nothing but its index, and Thunderbird never moves it off index 0. The `tabs` permission is there for the tab titles. The keys reach these commands from the mail tab, the reading pane, a message tab and a message window. In a message window `tab.next` and `tab.prev` refuse, since there is one tab.
- `handlers/message.ts`, `handlers/message_state.ts`, `handlers/compose.ts`, `handlers/identity.ts`: archive and delete, the state and move handlers, the compose handlers and the identity guard. They take the API subset in a scope object and never read a global.
- `handlers/clipboard.ts`: yank and open. Yank writes plain text with `navigator.clipboard.writeText` (measured to work from the background page with no user activation on both apps, the `clipboardWrite` permission is set). The first selected message decides. `msg.open` refuses a selection of more than one message.
- `commands/attachments.ts`, `handlers/attachments.ts` and `safe_filename.ts`: `msg.save_attachments {where}` (key `g a`). The handler lists the attachments of each selected message, saves each through a blob URL to `DesertBird/<date>-<subject>/<name>` with `conflictAction: uniquify` and ends once the downloads start, skips inline and removed parts, and revokes each URL when `downloads.onChanged` ends its download (ten-minute fallback). `safe_filename` is pure and cleans every name taken from mail. It notifies the count and folder, and never opens a file.
- `commands/snooze.ts` and `handlers/snooze.ts`: `msg.snooze {until}` (keys `m z l`, `m z t`, `m z w`, `m z m`). The handler moves each selected message to a `Snoozed` folder in its own account, created on first use, and falls back to the Local Folders `Snoozed` folder only when the account root cannot hold subfolders. Any other create failure, a create that gets no answer in 10 seconds included, refuses the snooze and leaves the message in place. Two snoozes at once in one account share one create. It then stores the Message-ID header, the origin account, the Snoozed folder id, the origin folder id and the due time. `main.ts` adds the wake as an `on_due` listener before `start`: `wake_snoozed` queries only the stored folder for the header (every page), moves it to the origin account's Inbox (never the folder it came from, which can be a Gmail label view), marks it unread and notifies. When the stored folder is gone, the wake finds `Snoozed` again by path in the origin account and Local Folders and queries only there. A wake that cannot return the message (not found, or no Inbox, including an Inbox query that finds nothing yet) keeps its item and retries each tick. Once 30 minutes past the due time have gone, it drops the item with a notification and leaves the message where it is. Any other lookup error keeps the item for the next tick. A wake that fails keeps its item and the next tick repeats it, so the wake finds the message wherever the last try left it. Snoozing a message that already sits in `Snoozed` only changes the time.
- `quick_reply_store.ts`: the nine quick reply texts under `desertbird_quick_replies`, as `{record_version, slots}` on the record store, with `migrate_quick_reply_record` as the migration hook. An empty string is an empty slot. The options page writes it and the background reads it.
- `commands/quick_reply.ts` and `handlers/quick_reply.ts`: `msg.reply_with {slot}` (keys `g r 1` to `g r 9`). An empty slot refuses with a message. Otherwise the handler opens a reply to the sender as `r` does (the newest message of a collapsed thread, an identity resolved first), reads the draft with `getComposeDetails` and writes it back with `setComposeDetails` with the text above the quote. Plain compose gets the text and a blank line in front of the body. HTML compose gets one `div` per line before the first quote node, set as `textContent` in a `DOMParser` document, so the text is escaped and never read as markup. It opens a draft and never sends.
- `commands/followup.ts` and `handlers/followup.ts`: `msg.remind {after}` (keys `m f d`, `m f t`, `m f w`) and `msg.remind_cancel` (`m f c`, which also clears the `Follow up` tag). Kept apart from snooze: a reminder moves no mail and shares only the scheduler. `main.ts` adds `fire_followup` as an `on_due` listener. `main.ts` holds the listener for 5 minutes after each background start, because the folders have not synced yet and a reply that came while Thunderbird was closed is not in them. At due it looks the anchor up by Message-ID (the anchor's account first), then reads the headers of the messages in the account's Inbox and Archives folders (subfolders included, since archives are filed by year) that are newer than the anchor. A header that cannot be read is skipped. A message whose `References` or `In-Reply-To` names the anchor is a reply, and the item is dropped with no notice. A reply that came while Thunderbird was closed is found by the first run after the grace, once the folders have synced. An anchor that is gone, or sits in Trash or Junk, drops the item with no notice. Otherwise it tags the anchor `Follow up` (created on first use, a tag failure is only logged) and shows a notification. The notification id carries the account and the Message-ID, so `open_followup_anchor` opens it on click with no state in memory. The notification is the last step, so a failed tag never repeats a shown notice. The notification call is a local function until `notify.ts` takes an id.
- `handlers/each_message.ts`, `handlers/displayed_folder.ts`, `handlers/special_folder.ts`: shared helpers. Loop over the selected ids with the empty-selection refusal, read the displayed folder, and find a folder by special use.
- `handlers/folder_open.ts`, `handlers/folder_marks.ts`, `handlers/jump_history.ts`, `handlers/folder_state.ts`: show a folder, the marks, the jump history and the one stored record they share. `show_folder` only shows. `show_folder_and_focus_threads` shows and then focuses the thread list through `focus_pane`, ignoring a refusal. `folder.open`, `mark.jump`, `jump.back`, `jump.forward` and `] U` use it, and folder search uses `show_folder` so the folder pane keeps the focus. `folder.open --tab` (`O` opens the command line on `open --tab `) calls `mailTabs.create` (which takes only `displayedFolder`) instead of `mailTabs.update`, so the folder shows in a new tab and the old tab keeps its folder. The command line closes and restores its old focus before it runs `:open`, so the new focus is the last one. `desertbird_folder_state` holds `{record_version, marks, history: {entries, cursor}}`, each folder as account id and path. `folder_state.ts` reads and writes through a queue, so a held `<C-o>` and the display events never overwrite each other, and it migrates an old record (a record it cannot read becomes an empty one). No memory copy exists: every command reads storage. `start_jump_history` runs from `main.ts` and records every folder the mail tab shows. The jump in progress sets a mark (tab, account, path) before `mailTabs.update` and clears it after. The display event fires before the update returns, while a held `<C-o>` already queues the next jump, so the listener drops the event that matches the mark before it queues. The cursor check in `record_displayed_folder` is the second guard. The listener also records the folder shown at start, since no event announces it.
- `commands/account_param.ts`: the `--account` flag, shared by the folder commands that take a folder path.
- `commands/help.ts` and `handlers/help.ts`: `help.open`, `options.open` and `help.whichkey`. The handlers open the help page or the options page, reusing a help tab that is already open, and `show_root_keys` lists the top-level keys in the which-key panel.
- `commands/search.ts` and `handlers/search.ts`: `search.open` (`/` and `?`), `search.next` and `search.prev`. `open_search` starts the live search, then opens the command line as a search line.
- `handlers/account_choice.ts`: `account_id_named`, which turns the `--account` value (a name or an id) into an account id and refuses an ambiguous name.
- `handlers/cmdline.ts`: `open_cmdline`, which stores the command line session (with the kind `window` when the key came from a message window) and then mounts the overlay.
- `handlers/folder_collapse.ts`: `collapse_folder` (`folder.collapse`, no default key). It folds the folder pane row, and from any other pane it focuses the folder pane.
- `handlers/loading.ts`: `while_loading`, which turns the first-display error of a mail tab query into a refusal that says the folder is still loading.
- `handlers/thread_view.ts`: the thread list motions: step to a thread root, move left and right through folds, reposition the view, half page and fold all. `h`, `l`, `z M` and `z R` fold folders when the folder pane has focus. They act on the thread list when it has focus or when the folder pane script is absent.

## Rules

- Every command states `bridge`. True only for a command that moves the view, the selection or the front tab harmlessly (`motion.*`, `tab.next`, `tab.prev`, `tab.switch`, `tab.goto`, `tab.alternate`). False for anything that changes mail, sends, discloses data or is hard to undo (`msg.*`, `tab.close`). The view commands change only what the list shows, so they are true.
- `needs` lists the Experiment verbs a command depends on (`keys.install`). The router refuses the command when one of them is not loaded. No phase 1 command lists one.
- Handlers act on the ids taken at the key press and never read the selection themselves. The selection can move between the key and the handler. The state keys act on every id, one call per id. `a` and `d d` act on every id in one call. `m r` and `m u` take the ids of a count too, then call once per id with one undo entry. With a count they also take the rows below the current one from `app.viewRows`, and refuse when the current row is not one the key selected or a closed thread falls in the range. A toggle (`msg.read` toggle, `msg.flag`, `msg.junk`) reads the first message and gives every selected message the opposite state. A failure part way stops the loop and the refusal says how many messages changed. `r`, `R` and `g F` use the newest message by date.
- A handler throws `RuntimeRefusal` for a state it cannot act on. It never checks an argument value, since the param schema does that.
- `msg.reply`, `msg.forward` and `msg.new` resolve an identity before any compose call (`resolve_identity`): one the message was addressed to (its own account first, then any), else the message account's first identity, else the default account's, else any. They refuse only when no identity exists. `beginReply` crashes the whole app with no identity anywhere, `beginForward` hangs unless the call names an identity when there is no default account, and `beginNew` opens a window that cannot send. Reply and forward pass the resolved identity.
- `msg.tag`, `msg.move` and `msg.copy` take a typed value, so their keys (`m t`, `m m`, `m c`) open the command line with the command started. `msg.move` and `msg.copy` take a folder path such as `/Archive` and look it up in the account `--account` names, else in the one account the selected messages share, and refuse a selection that spans accounts. A copy records no undo item, since the originals stay. `folder.open` takes the same `--account`. `folder.read_all` refuses in a saved search, because the API would mark every message in its source folders read.

## Traps for later phases

- `mailTabs.update({displayedFolder})` throws "An unexpected error occurred" on the first display of a folder with messages, although the folder displays. The console shows `this._sort[0] is undefined` from `DBViewWrapper`. `show_folder` treats that error as success only when a query right after shows the folder or throws the same error (see `thunderbird-behavior.md`, Phase 2: folders and jumps).
- `tabs.remove` does nothing on the primary tab.
