# Hud, background side

The which-key panel and the toasts of each main window and message window, and the mode label of the status bar of a main window and a message window. The page (`src/overlay/hud.ts`) only draws the panel and the toasts. This side decides what shows and when, and mounts the page while something shows. The label is no page: the Experiment draws it in the status bar and this side tells it what to show (`overlay.setModeLabel`).

| File | Role |
| --- | --- |
| `service.ts` | One state per window: the typed keys the panel lists, the toasts, the mode (visual or resize) and a mount flag. Reads `pending` and `mode` events, answers the page's `hud.state` message and tells a mounted page to ask again (`hud.changed`). Mounts the `hud` surface while something shows and unmounts it when nothing does. `mode_of` gives the bridge the mode of a window |
| `which_key.ts` | Pure: the continuations of a typed prefix from the compiled tree, with the chain of group names as the title, and whether the panel may open on its own (`which_key_delay_ms`, `which_key_skip`), and `with_stored_marks`, which swaps the capture row under `M` and `'` for one row per stored folder mark |
| `toasts.ts` | Pure: the stack of toasts of one window, each with its own timer. Timers come in as a parameter, so tests move the clock |

## Rules

- A message document reports its typed prefix as a `body.pending` request, which `body_requests.ts` hands to `on_body_pending` with the window of the sender. The panel shows in the mail tab, in message tabs and in a standalone message window. `main.ts` tracks each of them (`track`, with `kind` `message` for a message window), and the hud drops the reports of any window it does not track. The panel then lists the message keys (`message_tree`) and not the mail window keys. An options or help page sends `tree: "own"` with its report, and the panel lists `own_tree`. A message window sends `tree: "window"`, and its header sends `source: "window"` on `pages.onInvocation`. `on_keys_event` drops the `pending` and `mode` events of any window it does not track, as `on_body_pending` does. Each window remembers the source of its panel, so a redraw reads the same tree, and the newest report of either source wins.
- The chrome runtime reports only the typed prefix, as a `pending` event on `keys.onInvocation`. It adds a tab change and a window blur to nothing: the background hears those from `tabs.onActivated` and `windows.onFocusChanged` and calls `close_which_key`.
- A compose window is tracked with `kind` `compose`. Its runtime reports the typed prefix as a `pending` event with `source` `compose` on `composewin.onInvocation`, and `main.ts` hands it to `on_keys_event`. The panel lists `compose_tree`, with the send key left out while `compose_send` is off (`without_leaf`). A compose window gets no label call and no toast: `toast` returns false for it, so the caller sends a system notification. A closed window leaves through `forget` like any other, and the runtime reports an end for a window that closes with a prefix pending.
- `state_of` hands `read_marks` to `with_stored_marks`, which calls it only under a mark capture (`read_folder_state` of `handlers/folder_state.ts`, which also holds the mark key format) on each redraw of that panel, so a mark set while the panel is up shows on the next redraw. A failed read leaves the capture row.
- The panel opens after `which_key_delay_ms` of a pending prefix. A delay of 0 turns it off. A prefix in `which_key_skip` (typed keys joined, for example `gu`) opens no panel by itself. A panel that is already up redraws at once for a longer prefix, as in DesertFox.
- `help.whichkey` (`g?` and `, ?`) calls `show_root`: the panel of the root keys shows at once, with no delay and whatever `which_key_delay_ms` says. The key runtime keeps its `pending` report armed after that command, so the next key in the mail tab, or in a calendar, address book or settings tab, reports an end and removes the panel. A page tab does not send the command: its runtime sends a `pending` event with no keys, `root: true` and `source`, which the hud turns into `show_root` of that source (`page` reads `page_tree`, `message` reads `message_tree`). A half-typed prefix in a page tab is a `pending` event with the same `source`, so the panel lists the keys of the tab and not the mail keys. A message document does not take this path, so `g?` there opens the help page instead.
- A toast lasts `toast_error_ms` for a refusal and `toast_ms` for a result. A time of 0, a missing window or a missing Experiment sends the message to a system notification instead, so no message is lost. A toast for `a`, `d`, `m s` and undo in a message window draws in that window. A window the hud does not track leaves the table again when its toast fails, so its later key reports stay dropped.
- The mode label follows `mode_indicator` (`always`, the default, `not_normal` or `off`) and `mode_indicator_style` (`classic`, the default, or `badge`). The key runtime reports `mode` events, `visual` or `resize` when that mode starts and `normal` when it ends. The service keeps that per window and sends it with both settings and the label colors of the `theme` setting (`src/background/theme/palette.ts`) to `overlay.setModeLabel` on each change, at `track` (a window open at start or opened later) and on a settings change. The Experiment turns the mode into insert while a text field has the focus and applies `mode_indicator` to the result, so insert mode never crosses to the background. The label mounts no hud page. A message window draws the label in its own status bar like a main window. A hidden status bar hides the label with it. `track` with `kind` `compose` sets no label, so `sync_label` makes no call for it.
- Settings are read through the config store on each use, and `storage.onChanged` on the settings key calls `settings_changed`, so a panel that shows redraws with the new border and the label changes or goes without a restart. A delay or toast time change applies to the next panel or toast.
- Toasts stay at the bottom right while the command line is open, and the hud box sits one z-index step above the command line box, so a toast draws over the panel. DesertFox puts its toasts below the command line, so the list hides them there. DesertBird keeps them visible, because a toast that is hidden still counts as shown and sends no system notification. The confirm prompt fills the box, so a mount through `lifting_toasts(..., true)` tells the service and the page moves its toasts up (`lifted` in the state). The command line mounts through `lifting_toasts(..., false)`, which sets the lift down. A toast counts as shown only when the page mounted. Otherwise `toast` answers false and `notify.ts` sends a system notification.
- A keymap reinstall closes the panel, because a new matcher forgets the sequence without a report.
- State is in memory only (an exception recorded in `AGENTS.md`): a few seconds of interface state per window, like the command line session. The page keeps none, and the background restart drops all of it.
- A bridge confirm prompt (`../bridge/confirm.ts`) borrows the command line surface and mounts it through `lifting_toasts(..., true)`, so toasts move above it.
- The hud page and the command line page are separate surfaces, so a toast or the panel never replaces the command line. The command line box sits above the hud, and a key that opens the command line ends the pending sequence first, which removes the panel.
