# Body script

The script that runs in each message document: the reading pane, a message tab and a message window. It gives the message keys while a message is read. The manifest key `message_display_scripts` injects it, and `tools/build.mjs` bundles it to `content/message_display.js` with its own size guard.

| File | Role |
| --- | --- |
| `message_display.ts` | The entry: hands the document window and `browser.storage` to `start_body_script`, with the `body.hints` request that asks the parent to label the header and the body, then asks the background with `body.tree` which tree the document runs and switches to `window_tree` in a message window. It asks again each second for 30 s while the background cannot answer |
| `page_keys.ts` | The entry of DesertBird's own pages: the same `start_body_script`, bundled to `content/page_keys.js` and loaded by `options.html` and `help.html` |
| `body_keys.ts` | Key handling and the fixed table of actions. Takes its window, storage and runtime as arguments, so node tests drive it with stubs |
| `body_find.ts` | Find in the message with `window.find`, and `n` and `N` with a wrap done by the script |
| `compose_keys.ts` | The entry of the compose script, which the background registers with `composeScripts.register` and `tools/build.mjs` bundles to `content/compose_keys.js` with its own size guard |
| `compose_edit_key.ts` | Ctrl+E in a compose body: it sends `compose.edit`, in either mode, once per press. Takes its window and runtime as arguments, so node tests drive it with stubs |
| `body_hints.ts` | Hint labels of the body alone: collects the clickable elements on screen, draws the labels, focuses the one typed. A message uses them when the parent cannot label it, and the own pages always |

The options and help pages are content tabs, which the main-window runtime does not serve and the manifest injects nothing into, so they load `page_keys.js` themselves and get the own page keys (`own_tree`, the reading keys with the commands a page can serve): `q` closes the tab, and `:`, `g?`, `j`, `k`, `gg`, `G`, `<C-d>`, `<C-u>`, `f` and `/` work. The keymap editor takes bindings as typed text in inputs, so no recording mode exists to step aside for, and keys typed in an input or a text area pass. In a select, Escape leaves the select, j and k step its options, and other keys pass. On a page `f` clicks the picked link or button by script, since the trusted Enter works only in the message pane. A page has no displayed message and no thread list, so it gets no mail key. A mail sequence that the tree lacks ends in a leaf that runs nothing, and a mail key of one token reaches the page unhandled.

## Rules

- The key matcher is the vendored one, through `../shared/keymap_tree.ts`, the same reader the chrome runtime uses. Never write a second matcher.
- The tree is the `message_tree` of the keymap record (an own page reads `own_tree`, the page keys with find and hints) the background keeps in storage under `KEYMAP_STORAGE_KEY`. The script reads it at load and follows `storage.onChanged`. Until a tree is in, it touches no key.
- The body script reads `message_tree` (message documents), `window_tree` (a message document in a message window, message mode) or `own_tree` (own pages). Only the background can tell a message window from a tab, so the document starts on `message_tree`, and the entry asks the background and switches the tree (`start_body_script` resolves to that switch). `src/background/commands/tab_keymaps.ts` builds them from the one keymap, filtered by each command's needs, so user bindings reach them. The reading keys are `j`, `k`, `<C-d>`, `<C-u>`, `gg` and `G`, with a count. The mail keys run in the background through `body.invoke` on the shown message. Keys that need the thread list or the mail tab (motions, thread, step, folders, view, marks) stay out. Escape ends a half-typed sequence or a count and goes on to Thunderbird. In insert mode the Escape that leaves the mode is cancelled in the bubble phase on `window_tree` only, since Thunderbird closes a message window on an Escape nobody cancelled. Capture does not cancel it, because the shared rule in `../chrome/escape_rule.ts` reads a cancelled Escape as used. A fixed table maps each id to a scroll. An id that is not in it does nothing.
- A plain printable key is cancelled whether or not it matched, so Thunderbird's single-key shortcuts (`a`, `r`, `#`) do not fire while a message is read. Named keys and chords the keymap leaves free pass. A key in a text field passes.
- `j` and `k` scroll `message_scroll_step_px` (default 40, `MESSAGE_SCROLL_STEP_PX` in `../shared/protocol.ts`). The script reads it from the settings record under `SETTINGS_STORAGE_KEY` and follows `storage.onChanged`. A value that is not a positive number gives the default.
- The window losing the focus ends a half-typed sequence, so `d`, a tab switch and `d` does not trash a message.
- A leaf that runs in the background (`/`, which opens the command line with `find ` typed, and every mail key) goes to the background as a `body.invoke` request. The request names a command and its args. The window and the messages come from the sender. The background runs it only for a command that a key of the stored message, window or own tree binds (default or user key), through the router and its one validator. The script itself ignores a key event that is not trusted, so a script in the mail cannot press keys. In a message window the command line keys of the window tree (`:`, `m t`, `m m`, `m c`) go this way too.
- The typed prefix of a half-typed sequence goes to the background as a `body.pending` request, for the which-key panel. The panel shows in the mail tab, in message tabs and in a standalone message window. The script sends it only when the prefix changes, and sends an empty prefix when the sequence ends (a match, a key with no match, Escape, a text field, a lost focus or a new tree). A plain key with no sequence sends nothing. Backspace in a half-typed sequence drops its last key and reports the shorter prefix, then is cancelled.
- `search.message` (typed as `find <text>`) runs in the background and sends `body.find` to the front tab. The script clears the selection, finds from the top with smart case (a capital letter makes it case sensitive), selects the match and focuses the message. `n` and `N` step to the next and previous match and wrap at the ends. They do nothing before a first find.
- `; f` (`hint.pick` with `action: focus`, focus only), `; c` (`action: activate`, the same as `f`) and `; y` (`action: yank`) are three keys under the prefix `;`, so which-key lists them. The labels show at once. A yank labels only elements with an address or text and sends `body.yank` with the link address, else the trimmed text, to the background, which writes the clipboard. The compose script is not touched.
- In a message, `f` and the `;` keys first send `body.hints` to the background, and the `hints` Experiment labels the message header and the body as one set and takes the keys itself (see `docs/design.md`, "Hints in a message"). Plain keys are dropped until the answer, at most 1.5 s, so a key typed before the labels draw runs no command. A scroll, a blur, a click, Escape or a keymap change drops a pick whose answer is still out and keeps the hold. When the answer is below 0 (a remote body) or the request fails, the script labels the body itself as below. The own pages pass no such request and always label themselves.
- `f` (`hint.pick`) labels the links, buttons and form controls that are on screen and puts the labels in the document. While they show, every key is for them: a letter narrows the labels, a label that is unique focuses its element and, for a link or a button, sends `body.open_link` to the background, which has the `hints` Experiment press a trusted Enter in the window. Thunderbird treats that as a click on the link (its external open and its check for a link that lies about its address run). A form control only gets the focus. The script never calls `click()`, since an untrusted click skips that handling. Labels are shown only for elements a mouse would hit (drawn, visible, on top at their centre, not disabled), sit in a closed shadow root of a container with inline `!important` style, and end on any other key, `Escape`, scroll, blur, a pointer press and when the keymap record goes away. The alphabet and the generator are `../shared/hint_labels.ts`, with no DOM in them, and the on-screen check is `../shared/hint_view.ts`; the hints of the mail window use both. The labels take the theme as literal declarations: the background publishes them under `HINT_STYLE_STORAGE_KEY` (`light-dark()` pairs of the `primary` and `bg_core` roles) and the script puts them in the inline style of each label, so no style sheet or custom property of a mail can recolor or hide them. The script reads them once per document, so a theme change shows on the next message. Before the first publish the labels are yellow. Only the top document is labelled.
- The handoff with the chrome runtime is the attribute `BODY_SCRIPT_LIVE_ATTRIBUTE` from `../shared/protocol.ts`. The script sets it on the root element once it holds a tree and removes it when the tree goes. While the chrome runtime sees it on the message body under the focus, it stops swallowing reading-pane keys. It is an attribute and not an Experiment verb, so the verb table stays fixed.
- The compose script takes Ctrl+E only, Caps Lock or not and no other modifier, and asks `compose.edit` in either mode. The modes, the other keys and the mode label of a compose window belong to the chrome runtime (`../chrome/compose_runtime.ts`, see [`../../docs/design.md`](../../docs/design.md), Compose normal mode). It listens at the window root, above the body, so a key it takes never reaches this script. It passes every chord, so Ctrl+E does. The script imports only `../shared/protocol.ts` and its own files.
- Import nothing from `../background/` or the vendored registry. The build test fails the bundle if it does. The only file taken from `../chrome/` is `focus.ts`, for the text field check.
