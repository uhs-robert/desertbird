# Chrome runtime

The privileged part of the add-on. It runs inside the Thunderbird process as the parent scripts of the Experiment APIs. The `keys` script loads at startup, holds the key runtime and listens for keys in the main mail window. The other APIs (`app`, `folderpane`, `hints`, `overlay`, `pages`, `zoom`) each have a bundle of their own. The schema is [`../experiment/keys.schema.json`](../experiment/keys.schema.json). The call shapes are in [`../shared/protocol.ts`](../shared/protocol.ts).

| File | Role |
| --- | --- |
| `parent_keys.ts` | The entry of the `keys` API: `get_keys_api` and `shutdown`. Holds the one runtime and the event subscribers |
| `platform.ts` | The Thunderbird globals the parent reads, and the guard that rethrows `ExtensionError(message)` from each verb |
| `focus.ts` | Where a key is going: a text field, the pane that holds the focus, the reading pane (and whether the body script is live in it) or an open menu and whether it takes a key. Follows the focused element through shadow roots and into browser documents. `is_text_field` and `blur_text_field` serve the typing keys of the page bundle: a text field is not the overlay's browser or a live message body |
| `runtime.ts` | Key handling. Takes its Thunderbird access as `RuntimeDeps`, so tests use fakes |
| `parent_overlay.ts` | The entry of the `overlay` API (`mount`, `unmount`, `onClosed`). Builds the remote `browser` element and loads the command line page into it |
| `parent_hints.ts` | The entry of the `hints` API (`sendEnter`, `pick`). `sendEnter` presses a fixed Enter through the text input processor in the main or message window with the given id. `pick` collects the targets of the front tab (the mail tab, or the window and the readable page of any other tab), or, for a web page or another add-on's page whose page actor is on, focuses the browser and asks the actor's child to label the page (`DesertBird:Hints` with the colors and the action, answered with a count), starts the labels and takes an optional `action` (`focus`, `activate`, `yank`), and takes the keys on `window.windowRoot`, the parent of the window in the event path, so a hint letter reaches the labels before the key runtime sees it. While the labels show it sets `data-desertbird-hints` on the window's root element, and `parent_pages.ts` passes every key then, because the page keys listen on the same window root ahead of the pick. With `place: "message"` (the body script's `f`) it follows the focus chain to `#messagepane`, labels the header of `about:message` and the body as one set, and answers 0 when the focus is no longer in a body and -1 for a remote body or a window with no tabs, so the body script labels the body itself. A picked body link or button gets the trusted Enter from a timer after the key, and only while the focus still sits on it. The labels end on a pick, a key no label continues with, `Escape`, a scroll or a pointer press in any of the documents, the window losing the focus, a tab change, another message loading (`MsgLoading`, message place only) and a shutdown. The yank text goes to the clipboard through `nsIClipboardHelper`, called inside the key event. Its own bundle and size guard |
| `hint_pick.ts` | The hint mode over a `PickHost` and a list of `PickTarget`s, so tests use fakes. Draws each document's labels in its own closed shadow root with the theme colors, narrows on typed letters (a label that stops matching goes), and runs the action on the picked target: its act, its focus, or a copy of its text. A target that left its document (another message loaded) is not acted on. A yank labels only targets with text. Labels come from `../shared/hint_labels.ts` |
| `hint_targets.ts` | What a hint can point at and what a pick does. Buttons, toolbar buttons, tabs and fields of the window, `about:3pane` and `about:message` (a click, a focus, or selecting the tab), the folder rows (the index setter, which opens the folder) and the thread rows (`selectedIndex`, which selects only). Each target also has a focus step (the same as the act for a row) and a yank text: the `href`, else the trimmed text, the folder name for a folder row and the subject cell for a thread row. Controls inside a row get no label of their own. The thread list keeps the focus after a pick. `collect_page_targets` serves any other tab: the controls of the window and of the tab's page, from a wider selector with links, check boxes, list items and the click roles. `collect_window_targets` gives those of one document, which `page_hints_child.ts` labels in a web page. `collect_message_targets` serves the message place: the header of `about:message` (controls, one label per address pill and per split button, tags, attachments) and then the body's links, buttons and fields. A tag takes the focus, an attachment is selected in its focused list, a pill's yank copies its address, and a body link or button is focused and then handed to the Enter. A pick clicks a check box or a radio button in every scan. These two walk open and closed shadow roots (`moz-*` controls keep their button there), the mail tab's scan does not |
| `overlay.ts` | Mount, replace and remove logic per window over `OverlayDeps`, so tests use fakes. A second mount replaces the first. A tab change or a closing window removes the overlay and fires `onClosed` |
| `parent_pages.ts` | The entry of the `pages` API (`install`, `onInvocation`): the keys of every tab that is not the mail tab. Listens on `windowRoot ?? window`, ahead of the key runtime, and holds no key of the mail tab. It runs in a bundle of its own because the admission rule keeps it out of `keys.js` |
| `page_runtime.ts` | Key handling of the other tabs over `PageDeps`, so tests use fakes. Two trees (the page tree and the message tree of a message tab), its own hold after a command that opens the overlay, its own end report of the key list. It reports the typed prefix and `g ?` as `pending` events that name their tree (`source`: `page`, or `message` in a message tab), because the background cannot tell which tree the front tab runs. An unbound key passes to Thunderbird. `on_child_key` runs a key the page actor's child took, with the child's field bit in place of the chrome's focus reading, and a null key (a hello from the front tab's child: a new page, or a key typed in the page's field) ends insert mode and the half-typed sequence, as a tab change does. Every set of the insert flag goes to the actor (`ChildPort`), so the child's walk starts over with each reset. In a page of another process the chrome leaves every key to the actor's child while it is on and the page's top-level document has the focus. Otherwise only the close chord (`tab.close`) runs |
| `page_actor_parent.ts` | The parent half of the page actor, built as the ES module `experiment/page_actor_parent.sys.mjs`. `parent_pages.ts` loads it from a `resource://` root named afresh each load, and the actor system loads the same URL, so both share its state. `start` registers the actor `DesertBirdPage` (web, file and `moz-extension` pages, top-level only) and reaches the pages already open. Answers each child's hello with its state (on or off, the window's insert flag, the skeletons of the page and typing trees: tokens and branches, with leaves marked `run`, `insert` or `normal`), pushes the state again on `set_keys` and `set_insert`, and hands the front tab's keys to the page runtime, rebuilt field by field. `takes_keys`, `scroll` and `blur` serve the runtime. `stop` turns the children off, unregisters, drops the root and drops the hooks |
| `page_actor_child.ts` | The child half of the page actor, built as `experiment/page_actor_child.sys.mjs` and run in the page's process. Reads the key and whether a text field has the focus (DesertFox's `takes_typing` and its shadow walk, plus `select` and design mode), walks the page skeleton as the parent's matcher does (a count, a prefix, a capture branch, Backspace) and cancels and sends only a key the walk takes, sends a key that breaks a prefix uncancelled so the parent ends the sequence, says hello again when a key typed in a field breaks a prefix (so the parent ends its sequence and gets no text), follows the leaves that enter or leave insert mode at once, drops plain keys at once in insert mode, sends Escape after the page's handlers with whether one used it, and runs the `Scroll` and `Blur` the parent sends. On `DesertBird:Hints` it loads `page_hints_child.sys.mjs` beside itself and answers with its count. While hint labels show it hands every keydown to them, and any state push ends them. It may bundle only `page_actions.ts` and the key token reader (`test/build.test.ts`) |
| `page_hints_child.ts` | The hint labels of a web page or another add-on's page, built as `experiment/page_hints_child.sys.mjs`, which the actor's child loads on the first pick in its process. `start` runs `hint_pick.ts` over the page's controls (`collect_window_targets`), sets the child's `pick` (its key reader and end) while the labels show, ends them on a scroll, a pointer press or `pagehide`, and copies a yank through `nsIClipboardHelper` in the page's process. Only the count goes back. It may bundle only the pick, the targets and the shared hint files (`test/build.test.ts`) |
| `readable_focus.ts` | What a key meets in the front tab, read from the focus chain: `pass` (the mail tab or an open menu), `typing`, `remote` (the chain ends in a browser the walk cannot enter, or nothing in the tab has the focus and the tab's browser is remote), `page` or `message` (a message tab with the focus outside the body, which takes the message tree) |
| `page_actions.ts` | The fixed table of reading actions by command id (`page.scroll_down`, `page.scroll_left`, `page.page_down` and the rest, with the `message.*` ids of the same scrolls). `scroll_axis_of` gives the axis of an id, so a sideways key finds a target that overflows in width. The scroll target is the nearest scrollable ancestor of the focused element, else the scrolling element of its document, else the largest scrollable element of it |
| `page_focus.ts` | Hooked from the overlay API. On `TabSelect`, focuses the front tab's browser when it is remote and the focus sits on the window body or the tab strip, so a remote page gets its first keys with no click |
| `overlay_id.ts` | The element ids shared by the overlay parent and the key runtime. The hud has ids of its own, and so does the mode label |
| `mode_label.ts` | The mode label at the start of the status bar, over `ModeLabelDeps` so tests use fakes. `set` finds the elements with the label id, keeps one, removes the rest and draws the text and colors for the mode and the style. It reads focus for insert mode and redraws on focus events and when Thunderbird's color scheme changes. The colors arrive with the call, for both schemes, and the label takes the scheme its window shows. `shutdown` removes the label from every main window |
| `motions.ts` | The fixed motion table: `motion.down`, `motion.up`, `motion.top`, `motion.bottom`. Pure functions over a `ViewPort` |
| `parent_folderpane.ts` | The parent of the `folderpane` API, a bundle of its own that Thunderbird loads on the first call and not at startup. Its verb `fold` opens or closes the selected folder (`row`), every folder (`all`) or closes the selected folder or else its parent (`parent`), and answers false, doing nothing, unless the folder pane has the focus. `focused` reports that focus. Folder tree verbs belong here, not in `parent_keys.ts` |
| `parent_app.ts` | The parent of the `app` API, a bundle of its own that Thunderbird loads on the first call and not at startup. It joins `view_verbs` and `app_verbs`. Neither file may enter `keys.js`: `test/build.test.ts` checks the inputs of that bundle |
| `parent_zoom.ts` | The parent of the `zoom` API, a bundle of its own that Thunderbird loads on the first call. `get` and `set` read and set the zoom of the browser `getBrowser()` names in a main or message window, through the window's `ZoomManager`. Where there is none (calendar, tasks, a mail tab with no message) `get` answers null and `set` false |
| `app_verbs.ts` | The verbs `paneFocus`, `paneResize`, `appCommand` and `appOpenPage` of the `app` API. Each reads its target from a fixed table (pane focus targets, the one allowed command name with its controller, taken from the page that shows the message: the mail tab, a message tab or a message window, the three pages with their addresses), so no caller passes a function name or an address. `paneFocus` also takes `left` and `right`, counted from the pane `focused_pane` names, and refuses a collapsed pane or a message pane with no live body script |
| `pane_resize.ts` | `move_border` and `reset_sizes`, the two operations behind the `app` verb `paneResize`. It reads the boxes of the panes and splitters of `about:3pane`, picks the splitter that touches the focused pane on the axis of the move (and overlaps it on the other), takes the one after the pane when two touch,, sets its `width` or `height`, and fires `splitter-resized` on it, which makes `PaneLayout` store the size. `reset_sizes` clears both splitters and the four stored values. It belongs to the `app.js` bundle and may not enter `keys.js` |
| `view.ts` | The thread list of `about:3pane` (`gDBView`, `threadTree`) behind a `ListPort`: the rows for the motions and the selected message ids for background commands. Also the check that the front tab is the mail tab, and `mail_pane_of`, which names a window by id and returns the `about:3pane` of its front mail tab (used by the `app` and `folderpane` parents, never by the key script). `ListPort.select_range` sets a range for visual mode |
| `view_verbs.ts` | The verbs `viewRows`, `viewThread`, `viewAllThreads` and `viewScroll` of the `app` API, which read and move the list for background commands. `viewRows` also returns the message flags word of each row, which the step commands read |

These files know Thunderbird's own markup, so a Thunderbird rename lands in one of them:
- `pane_resize.ts`: `paneLayout.folderPaneSplitter` and `messagePaneSplitter` (`resizeElement`, `resizeDirection`, `width`, `height`, `isCollapsed`, `isDisabled`), the ids `folderPane`, `threadPane` and `messagePane`, the `splitter-resized` event, and the XULStore ids `folderPaneBox` and `messagepaneboxwrapper` under the `messenger.xhtml` URL.
- `view.ts` and `view_verbs.ts`: `gDBView`, `getSelectedMsgHdrs`, `threadTree` and the tab mode `mail3PaneTab`.
- `app_verbs.ts`: `folderTree` (`selectedRow`, `expandRow`, `collapseRow`), `paneLayout` (`folderPaneVisible`, `messagePaneVisible`), `messageBrowser`, `commandController`, `DefaultController`, `openAddonsMgr`, `openContentTab` and `browsingContext.topChromeWindow`.
- `parent_zoom.ts`: `getBrowser()`, `ZoomManager` (`getZoomForBrowser`, `setZoomForBrowser`) and the window type `mail:messageWindow`.
- `focus.ts`: the element ids `folderTree`, `messageBrowser` and `messagepane`, the element names `search-textbox` and `menulist`, the popup `state`, the `open` attribute of `panel-list` and the `accesskey` and `hidden` attributes.
- `platform.ts` and `parent_keys.ts`: `#tabmail`, the `messenger.xhtml` URL and the window type `mail:3pane`. `parent_keys.ts` also reads `folderTree` (`rowCount`, `selectedIndex`) for the motions in the folder pane.

## Rules

- The `overlay` API has its own bundle, script and schema, and its own size guard. Its verbs take a window id and a surface name from a fixed list (`cmdline`, `hud`), and `setModeLabel` takes enums for the mode, the indicator and the style. The command line takes the keyboard and leaves on Escape or a tab change. The hud never takes it, stays across tab changes and goes only with its window or an `unmount`. One window holds one box per surface. The parent maps the name to a page of the extension and never takes a path or an address.

- Each Experiment API needs its own bundle, script and schema. Two manifest entries that shared one script left the second API unloaded.
- Import only the matcher side of `vendor/desertfox`: `keys/matcher`, `keys/token`, `prefix_tree` and `register_names`. Never import `registry/*`. Import `../shared/protocol.ts` for types and the body handoff attribute only, and `../shared/keymap_tree.ts` for the tree reader.
- `keys.install` takes the keymap as data. `root` is the branch of the normal mode. A leaf runs in the chrome only when its id is in the motion table. Any other id does nothing.
- With the folder pane focused, the motions move the folder selection (`folderTree.selectedIndex`, which also opens the folder) and not the thread list. Visual mode does not apply there. A background command still reads the thread list selection.
- A leaf with `runs_in: "background"` leaves as a `keys.onInvocation` event. Nothing else crosses the boundary, but the typed prefix: a `pending` event rides the same event with the typed key tokens (counts left out) and no keys when the sequence ends, so the background can list the keys that may follow. Backspace in a half-typed sequence drops its last key and reports the shorter prefix (`matcher_for_tree`, shared with the body script). A tab change or a window blur is not reported, because `keys.js` is at its size budget: the background hears those itself. The event carries the MailExtension ids of the messages selected at the key press (`messageIds`), read in the same key handler, so a `j` typed right after `a` cannot change what `a` archives.
- The ids come from `gDBView.getSelectedMsgHdrs()` (a collapsed thread counts as all its messages) and `messageManager.convert`, which builds a whole message header for each one. The cost grows with the selection: a select-all over a very large folder stalls the key press for that long. Motions never read the selection and stay fast.
- The first `keys.install` registers one `ExtensionSupport` window listener. Later calls replace the tree and add no listener. `shutdown` removes every key listener and the window listener, and drops the tree and the half-typed sequence.
- Keys run in the mail tab of the main window and, through the body script, in a message document. In every other tab the keys belong to the `pages` bundle (`parent_pages.ts`), which the key runtime leaves alone: it drops a half-typed sequence and returns. A key passes through when its target, its original target or the end of the focus chain is a text field (the quick filter, the global search). While a menu or panel is open, a plain printable key is swallowed unless the popup takes it. An open `menupopup` (the context menus) takes the `accesskey` of its direct items, which it consumes itself. An open `panel` or `panel-list` (the app menu) takes no plain key, with the focus inside it or not, because the app menu has no access keys and `j`, `a` or `n` would reach Thunderbird's shortcuts under it (the mail window has no `panel-list`, so that case costs nothing). Items of closed submenus and hidden panel views never count. Named keys and chords still pass. The search is one light-tree query (`menu_takes_key` in `focus.ts`). Another tab does not swallow: `readable_focus.ts` still answers `pass` for an open menu there. The thread list and the folder pane run keys. The overlay's `browser` is treated as a text field by its id (`overlay_id.ts`), so no key runs while it has focus. The browser has another id from the mount until its page sets its title, so plain keys are dropped for as long as the page is not ready, whatever the hold timer says (the hold itself covers the time before the mount focuses the browser). The mount blurs the window as it focuses the browser, so the overlay host stops the blurs of that one `focus()` call at the window root, above the runtimes' listeners (`focus_without_blur_reaching_runtimes`). Every other blur reaches them. If the ready title does not come within `READY_FAILSAFE_MS`, the host closes the overlay, gives the focus back and reports `onClosed` with `reason: "not_ready"`, and the background shows a toast. A page that is not ready is never a typing target. In normal mode an unbound plain printable key is swallowed. Unbound named keys (Enter, Escape, arrows, Tab, Space) and unbound chords (a key with ctrl, alt or meta) pass. A bound chord runs and is cancelled, like a bound plain key. With focus in the reading pane, the body script runs the keys when it is live in the message body (it marks the document, see [`../content/README.md`](../content/README.md)), and every key passes to it. Otherwise every plain printable key is swallowed and chords pass, so Thunderbird's single-key shortcuts do not fire there either.
- A half-typed sequence and a pending count end on any chord the keymap does not bind as its next key, and when a key goes to a text field, an open menu, the reading pane, another tab or another window. A chord the keymap binds as a first key then runs. A change of the front tab ends them too, however it happens (a `TabSelect` capture listener on the window), because a click on the tab bar sends no key. A blur of the window itself ends them as well (a `blur` capture listener on the window that ignores a focus move between elements), for example on an alt-tab.
- `.` is the command `repeat.last`, which `runtime.ts` runs itself and the motion table does not hold. It replays the last leaf that ran, motion or background, with the count it ran with. A count before `.` replaces that count. A replay reads the selection at the `.` key press, not the one the first run had. `.` never records itself. The last leaf lives only in chrome runtime memory. It is not user data and nothing can refill it, so the runtime that `shutdown` drops takes it along. The background tags steps of a command defined with `repeatable: false` (`msg.move`, `msg.snooze`, `msg.undo` and `cmdline.open`, among others) in the tree. Running such a leaf clears the last run, so a stray `.` never moves mail to a typed folder or snoozes it. `.` does repeat `a` and `d d`, with their count, because `u` undoes them. A `.` that breaks a half-typed sequence ends it and then runs as a first key, like any key the matcher retries.
- Resize mode is `pane.resize_mode` (`w r`), which `runtime.ts` runs itself, beside visual mode. `resize_window` names the window it runs in, with `resize_count` (the digits typed since the last move, up to the matcher's six). A key in another window ends the mode before any early return. Then a text field (`in_text_field`, which the body script of the reading pane is not) or an open menu ends it, and only then `h l j k =` emit `pane.resize` and Escape and Enter end the mode and clear the half-typed chord, so a chord prefix typed in the mode cannot complete later. Other plain keys are swallowed, and a chord falls through to the normal path with the mode still on. A tab change, a window blur, `shutdown` and a closed window clear it. `tell_mode` reports `resize`, `visual` or `normal` to the background once per change. A mode that starts in another window first clears the window that heard the old mode.
- Visual mode is `visual.toggle` (`v`), which `runtime.ts` runs itself. It keeps one anchor row. While it is on, a motion selects the range from the anchor to the new current row through `select_range`. A background leaf reads the whole range as `messageIds`. Unless the background tagged its step `keeps_selection` (`msg.read`, `msg.flag`, `msg.junk`, `msg.tag`, `msg.copy`, whose rows stay in the list), it ends the mode, so `a` or `d d` acts on it once. The default `m t` and `m c` bind `cmdline.open`, which is not tagged, so they open the command line and end the mode. A leaf of a command with `repeatable: false` still clears `.`, and `v` never records itself. `v` again ends the mode on the current row. Escape does the same, but only while the mode is on: otherwise it passes through, so the command line overlay and Thunderbird keep it. A tab change or a window blur ends the mode. So does any key that finds another current row, another view or other message keys at the two ends of the range than the mode last set (a click, new mail, a row inserted or removed inside the range, a sort or a folder change), or that goes to a text field or the reading pane, so a stale anchor never reaches into a changed list. After a command that ends the mode takes the range, the selection collapses to the current row, so a following `d d` acts on one message. That collapse can show the row in the message pane and mark it read. A range over collapsed threads includes their hidden replies, as in Thunderbird.
