# Chrome runtime

The privileged part of the add-on. It runs inside the Thunderbird process as the parent scripts of the Experiment APIs. The `keys` script loads at startup, holds the key runtime and listens for keys in the main mail window. The other APIs (`app`, `composewin`, `context`, `filter`, `folderpane`, `hints`, `menukeys`, `overlay`, `pages`, `zoom`) each have a bundle of their own. The schema is [`../experiment/keys.schema.json`](../experiment/keys.schema.json). The call shapes are in [`../shared/protocol.ts`](../shared/protocol.ts).

## Rules

- The `overlay` API has its own bundle, script and schema, and its own size guard. Its verbs take a window id and a surface name from a fixed list (`cmdline`, `hud`), and `setModeLabel` takes enums for the mode, the indicator and the style. The command line takes the keyboard and leaves on Escape or a tab change. The hud never takes it, stays across tab changes and goes only with its window or an `unmount`. One window holds one box per surface. The parent maps the name to a page of the extension and never takes a path or an address.

- Each Experiment API needs its own bundle, script and schema. Two manifest entries that shared one script left the second API unloaded.
- Import only the matcher side of `vendor/desertfox`: `keys/matcher`, `keys/token`, `prefix_tree` and `register_names`. Never import `registry/*`. Import `../shared/protocol.ts` for types and the body handoff attribute only, and `../shared/keymap_tree.ts` for the tree reader.
- `keys.install` takes the keymap as data. `root` is the branch of the normal mode. A leaf runs in the chrome only when its id is in the motion table. Any other id does nothing.
- With the folder pane focused, the motions move the folder selection (`folderTree.selectedIndex`, which also opens the folder) and not the thread list. Visual mode does not apply there. A background command still reads the thread list selection.
- A leaf with `runs_in: "background"` leaves as a `keys.onInvocation` event. Nothing else crosses the boundary, but the typed prefix: a `pending` event rides the same event with the typed key tokens (counts left out) and no keys when the sequence ends, so the background can list the keys that may follow. Backspace in a half-typed sequence drops its last key and reports the shorter prefix (`matcher_for_tree`, shared with the body script). A tab change or a window blur is not reported, because `keys.js` is at its size budget: the background hears those itself. The event carries the MailExtension ids of the messages selected at the key press (`messageIds`), read in the same key handler, so a `j` typed right after `a` cannot change what `a` archives.
- The ids come from `gDBView.getSelectedMsgHdrs()` (a collapsed thread counts as all its messages) and `messageManager.convert`, which builds a whole message header for each one. The cost grows with the selection: a select-all over a very large folder stalls the key press for that long. Motions never read the selection and stay fast.
- The first `keys.install` registers one `ExtensionSupport` window listener. Later calls replace the tree and add no listener. `shutdown` removes every key listener and the window listener, and drops the tree and the half-typed sequence.
- Keys run in the mail tab of the main window and, through the body script, in a message document. In every other tab the keys belong to the `pages` bundle (`parent_pages.ts`), which the key runtime leaves alone: it drops a half-typed sequence and returns. A key passes through when its target, its original target or the end of the focus chain is a text field (the quick filter, the global search). While a menu or panel is open, a plain printable key is swallowed unless the popup takes it. An open `menupopup` (the context menus) takes the `accesskey` of its direct items, which it consumes itself. An open `panel` or `panel-list` (the app menu) takes no plain key, with the focus inside it or not, because the app menu has no access keys and `j`, `a` or `n` would reach Thunderbird's shortcuts under it (the mail window has no `panel-list`, so that case costs nothing). Items of closed submenus and hidden panel views never count. One panel is the exception: while DesertBird's own toolbar popup browser holds the focus (Thunderbird marks it `webextension-view-type="popup"`, and its URL starts with the add-on's `baseURL`), the key counts as typing and goes to the popup page (`is_typing_target` in `parent_keys.ts`). Named keys and chords still pass. The search is one light-tree query (`menu_takes_key` in `focus.ts`). Another tab does not swallow: `readable_focus.ts` still answers `pass` for an open menu there. The thread list and the folder pane run keys. The overlay's `browser` is treated as a text field by its id (`overlay_id.ts`), so no key runs while it has focus. The browser has another id from the mount until its page sets its title, so plain keys are dropped for as long as the page is not ready, whatever the hold timer says (the hold itself covers the time before the mount focuses the browser). The mount blurs the window as it focuses the browser, so the overlay host stops the blurs of that one `focus()` call at the window root, above the runtimes' listeners (`focus_without_blur_reaching_runtimes`). Every other blur reaches them. If the ready title does not come within `READY_FAILSAFE_MS`, the host closes the overlay, gives the focus back and reports `onClosed` with `reason: "not_ready"`, and the background shows a toast. A page that is not ready is never a typing target. In normal mode an unbound plain printable key is swallowed. Unbound named keys (Enter, Escape, arrows, Tab, Space) and unbound chords (a key with ctrl, alt or meta) pass. A bound chord runs and is cancelled, like a bound plain key. With focus in the reading pane, the body script runs the keys when it is live in the message body (it marks the document, see [`../content/README.md`](../content/README.md)), and every key passes to it. Otherwise every plain printable key is swallowed and chords pass, so Thunderbird's single-key shortcuts do not fire there either.
- A half-typed sequence and a pending count end on any chord the keymap does not bind as its next key, and when a key goes to a text field, an open menu, the reading pane, another tab or another window. A chord the keymap binds as a first key then runs. A change of the front tab ends them too, however it happens (a `TabSelect` capture listener on the window), because a click on the tab bar sends no key. A blur of the window itself ends them as well (a `blur` capture listener on the window that ignores a focus move between elements), for example on an alt-tab.
- `.` is the command `repeat.last`, which `runtime.ts` runs itself and the motion table does not hold. It replays the last leaf that ran, motion or background, with the count it ran with. A count before `.` replaces that count. A replay reads the selection at the `.` key press, not the one the first run had. `.` never records itself. The last leaf lives only in chrome runtime memory. It is not user data and nothing can refill it, so the runtime that `shutdown` drops takes it along. The background tags steps of a command defined with `repeatable: false` (`msg.move`, `msg.snooze`, `msg.undo` and `cmdline.open`, among others) in the tree. Running such a leaf clears the last run, so a stray `.` never moves mail to a typed folder or snoozes it. `.` does repeat `a` and `d d`, with their count, because `u` undoes them. A `.` that breaks a half-typed sequence ends it and then runs as a first key, like any key the matcher retries.
- Resize mode is `pane.resize_mode` (`w r`), which `runtime.ts` runs itself, beside visual mode. `resize_window` names the window it runs in, with `resize_count` (the digits typed since the last move, up to the matcher's six). A key in another window ends the mode before any early return. Then a text field (`in_text_field`, which the body script of the reading pane is not) or an open menu ends it, and only then `h l j k =` emit `pane.resize` and Escape and Enter end the mode and clear the half-typed chord, so a chord prefix typed in the mode cannot complete later. Other plain keys are swallowed, and a chord falls through to the normal path with the mode still on. A tab change, a window blur, `shutdown` and a closed window clear it. `tell_mode` reports `resize`, `visual` or `normal` to the background once per change. A mode that starts in another window first clears the window that heard the old mode.
- Visual mode is `visual.toggle` (`v`), which `runtime.ts` runs itself. It keeps one anchor row and the rows selected at `v` (the base), which the mode never unselects. While it is on, a motion selects the base plus the range from the anchor to the new current row through `select_rows`, so a second `v` adds a range to a kept selection. A background leaf reads the whole selection as `messageIds`. Unless the background tagged its step `keeps_selection` (`msg.read`, `msg.flag`, `msg.junk`, `msg.tag`, `msg.copy`, whose rows stay in the list), it ends the mode, so `a` or `d d` acts on it once. The default `m t` and `m c` bind `cmdline.open`, which is not tagged, so they open the command line and end the mode. A leaf of a command with `repeatable: false` still clears `.`, and `v` never records itself. `v` again, Escape or Space ends the mode, keeps the selection and starts a pick (below). A tab change or a window blur ends the mode. So does any key that finds the list changed (`list_seen`, below), or that goes to a text field or the reading pane, so a stale anchor never reaches into a changed list. A command that removes the selected rows leaves Thunderbird to pick the next row. A range over collapsed threads includes their hidden replies, as in Thunderbird.
- Space is `select.toggle`, which `runtime.ts` runs itself in the thread list (not in the folder pane). It toggles the current row with `toggleSelectionAtIndex` and the cursor stays. It swallows the key, because Thunderbird's own Space would select the cursor row alone about 270 ms later. The first Space on the one selected row keeps that row and only sets the pick flag (`picking`), since one selected row looks the same whether it was picked or only read. Leaving visual mode sets it too, and Space in visual mode only leaves the mode. In a pick, or with two or more rows selected, a motion moves only the current row (`move_cursor`, that is `currentIndex`) and the selection stays. Escape out of visual mode ends a pick and drops a selection of two or more rows to the current row, and is swallowed then. Otherwise it passes. `list_seen` holds the current row, the selected row numbers, the view and the message keys at them and at the current row after each key. A key that finds them changed (a click, new mail above the rows, a row inserted or removed, a sort or a folder change) ends the pick and visual mode. The pick also ends on a tab change, a window blur, a key that goes to a text field or the reading pane and a command that is not tagged `keeps_selection`. The flag lives in memory only, an exception listed in `AGENTS.md`. A cursor-only move focuses the list body, and `cursor_sheet.ts` outlines the current row, so the cursor shows on any row.
