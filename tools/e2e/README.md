# End-to-end run

Drives the built add-on in a real Thunderbird and a real Betterbird, headless. It reuses the session and fixture modules from [`tools/measure/`](../measure/README.md). Needs `labwc`, `wtype`, `wlrctl`, `grim`, `zip`, `unzip` and `node`.

```bash
tools/measure/fetch_thunderbird.sh      # once: Thunderbird 153.7.0 ESR into $MEASURE_DIR
npm run e2e                             # setup proof: start each app, take one screenshot
npm run build && npm run e2e -- --xpi dist/desertbird.xpi    # the key assertions, both apps, both profile kinds
E2E_KINDS=default npm run e2e -- betterbird --xpi dist/desertbird.xpi
E2E_SHARDS=3 npm run e2e -- --xpi dist/desertbird.xpi        # the pieces on 3 workers at once, see Workers
```

With `--xpi` the run installs DesertBird and the helper add-on, prints one PASS, FAIL or NOTE line per check and writes the report to `.logs/e2e-timings-<stamp>.report.json` and the screenshots under the run dir. A FAIL exits 1, and a bad setting (an unknown kind or section, a bad `E2E_SHARDS` or deadline) exits 2. A NOTE is a measurement with no pass condition. `E2E_KINDS` picks profile kinds (`default`, `reply_no_identity`, `mail_account`, `message`, `message_remote`, `quick_reply_plain`, `quick_reply_html`, `mode_label_badge`, `mode_label_off`, `mode_label_themed`, `own_pages`, `pages`, `zoom`, `web`, `compose_editor`, `compose_editor_html`, `compose_editor_html_top`). `E2E_ONLY=mode_label` runs only the label checks of the `default` kind. See Pieces for how `E2E_KINDS`, `E2E_ONLY` and `E2E_SCALE` pick what runs. The two message kinds run the body script checks in the pane, a message tab and a message window; `message_remote` lets mail load remote content. In the message window they also check message mode: in the body, Alt+H reaches Thunderbird and opens its Help menu (the window tree leaves the pane chords free, and a body on the message tree would swallow it); in the body and with the focus in the header (F6), `z i` and `z =` zoom (read from `innerHeight` in a fresh report that the helper's `report_window` asks the window's document for), `c` opens a new message, and the help, options and Thunderbird page keys open their page in the main window and bring it to the front; in the header `j` scrolls, `m s` flags, `/`, `H`, `n` and `N` do nothing and `q` closes; two windows at once (the helper's `focus_window` moves the focus between them) make no `g g` out of a `g` in each, read from a fresh report of the second window; and a key right after a window opens breaks nothing. The piece `default/filter_by_message` (`E2E_KINDS=default E2E_ONLY=filter_by_message`) builds its profile as `lists`, a profile kind and not an `E2E_KINDS` value: the default profile plus the Lists folder of `profile.mjs` (seven messages on two mailing lists and none, over three days). It checks that `b m l` and `b m d` show the mail of the selected message's list and day, that `b u`, `b s` and the `/` search keep the list filter and that Escape brings it back, that `b r` clears both, and that a message with no List-Id refuses with a toast and leaves the list as it was. The piece `message/header_hints` (`E2E_KINDS=message E2E_ONLY=header_hints`) builds its profile as `message_header`, a profile kind and not an `E2E_KINDS` value: the Header folder of `tools/measure/fixtures.mjs` (a message with Cc, a tag and two attachments) and the dark scheme, where the header shows its day/night switch. It checks `f` from the body over the header and the body in the pane, a message tab and a message window, `f` from the header of a message tab (F6 moves the focus there, and the body report's `has_focus` confirms it), `f` from the header of a message window, and `f` in the main window after a message window closed with its header labels up. The piece `message/window_cmdline` (`E2E_KINDS=message E2E_ONLY=window_cmdline`) checks the command line in a message window: `:` draws, two Escapes close it (a third would close the window) and the keys return to the body, `m t`, `m c` and `m m` from the body and the header, a command the window does not offer refused in the line, the window showing the next message after a move, two chrome windows each with a line, and a message archived through the helper under the open line (the window shows the next message, or closes for the last one). It also checks the which-key panel after `g` from the header and the body of the window, ended by a stray key, and the refusal toast of `m f c` drawn in the window. The piece `message/window_step` (`E2E_KINDS=message E2E_ONLY=window_step`) checks `J`, `K`, `] u` and `[ u` in a message window opened from the Reading folder: each step shows the next or previous message, and `K` at the first, `J` at the last, `] u` at the last unread message with an earlier unread one (where Thunderbird would wrap) and `[ u` at the first unread message show a toast and keep the message. A window opened from an .eml file is not driven (the helper cannot open one), so the unit tests cover its refusal. `quick_reply_plain` and `quick_reply_html` give the identity a signature and install a copy of the xpi that seeds the quick reply slots at startup, then check that `g r 1` keeps the quote and the signature. The `own_pages` kind installs a copy of the xpi that opens the options or help page when the helper add-on sends its name (another add-on may not open them through the tabs API), then checks that `q` closes each page and does not close the options page with an input focused. The `compose_editor` kind turns on `external_editor` and writes a `desertbird_host` manifest and an `editor.toml` with a fake editor into the session's own `HOME`. The manifest points at the DesertFox host in `~/.local/share/desertfox/desertfox-host`, or at `E2E_DESERTFOX_HOST`. It checks that Ctrl+E and Escape then `e` in a plain-text reply write the fake editor's text into the body, that `e` in insert mode types a letter, that a letter and Enter in normal mode leave the body unchanged, Tab and Shift+Tab type nothing, that `i` returns to typing, that `s` and Ctrl+S save a draft and the window stays in normal mode, that `z m` zooms the body, that `?` opens the help page in the main window, and that the mode label is in neither the body nor a saved draft (`save_draft_raw` of the helper). The piece `compose_editor/window` (Betterbird only, no editor host needed) checks the compose window hook: the status bar label reads NORMAL after Escape and INSERT after `i` (pixel region `980,696 90x22`), `g s`, `g t`, `g c`, `g b` and `g m` move the focus and enter insert mode (Cc and Bcc show their rows), a letter in normal mode types nothing in the Subject, To and the body while `i` types there (read from `getComposeDetails`, which the helper gives with `to`, `cc` and `bcc`), Ctrl+F in normal mode puts typing in the find bar, Escape with the address popup open (contacts made by the helper's `make_contacts`) closes it and keeps insert mode, `q` on a changed draft shows the save prompt and Cancel keeps the window and the text, and `q` on a draft with no change closes the window. `quick_reply_html` checks the same of a saved HTML draft. With no host there it prints a NOTE and checks nothing. The two `compose_editor_html` kinds compose in HTML and their fake editor writes Markdown with a bold word, an `onerror` image, a `javascript:` link and escaped tag text. They check that the Markdown comes back as HTML in the user's place, with the quote and the signature kept and nothing live from the Markdown: below the quote in a reply for `compose_editor_html`, above the quote and the signature for `compose_editor_html_top` (`reply_on_top`, signature above the quote). Each records the bodies before and after the editor as NOTE lines, the source of the fixtures in `test/compose_bodies.ts`. `compose_editor_html` also saves a draft with an embedded image, opens it again and records the image `src` as a NOTE. A forward is not driven: `g F` in this profile opened its window only after many seconds, with the focus in the To field. Two runs with one `E2E_DIR` cannot run at once, see Run dir.

The run opens the Inbox with keys only: the folder tree already holds the focus DesertBird gave it at launch and the Local Folders row, so Right expands it, Down opens the Inbox and F6 moves focus to the thread list. With a message shown, one F6 from the list reaches the message body and Shift+F6 returns. F6 cycles the folder pane, the thread list, the message body, the spaces toolbar and the global search on both apps, measured through the focus chain. Counted Tabs are not used: on Betterbird three Tabs from the folder pane end on a column header.

The follow-up checks set a reminder with `m f d`, read the stored record from the IndexedDB file of the add-on in the profile (the helper cannot read another add-on's storage), restart the app, and cancel with `m f c`. The due fire needs a clock run of a day and `src/` takes no test hook, so it is a hand check.

A reload or restart of DesertBird is a restart of the app on the same profile (`restart` in `harness.mjs`), because `management.setEnabled` is refused for an add-on in the profile folder and `src/` takes no test hook. `restart` in `ctx.mjs` records a check that the process id changed, so a skipped restart fails the run.

The three `mode_label_*` kinds install a copy of the xpi that seeds a setting at startup (`mode_label_badge` the badge style, `mode_label_off` the off indicator, `mode_label_themed` the badge style in the `oasis_sol` theme) and check the label against the strips of a classic-style reference app. Each of the three pieces starts that app first (`reference_strips` in `pieces/_mode_label.mjs`), takes the strips of the label in normal, visual and insert mode, stops it, and then starts its own app. The label is an element of the window and no page, so the checks compare the pixels of its strip (`LABEL_STRIP`): `v` and Escape, and focus in and out of the quick filter, change it and bring it back. A disable or reload of the add-on is not run, because `management.setEnabled` is refused for an add-on in the profile folder. Unit tests cover the cleanup (`test/mode_label.test.ts`).

The `mode_label_themed` kind seeds the badge style and the `oasis_sol` theme, then reads the badge fill pixels (`png_colors`) against the theme's mode roles for the scheme the status bar shows. `E2E_THEME=tb_dark_os_light` or `tb_light_os_dark` sets Thunderbird's scheme against the OS scheme, so a label that follows the OS fails. `E2E_ONLY=cmdline` runs only the command line checks (`run_cmdline`). `E2E_ONLY=cmdline_launch` runs only the launch-time check (`run_cmdline_launch`): a message selected, then `: j a` typed with no pause. `E2E_ONLY=threads` runs only the thread keys (`run_threads`), with the barrier check first. `E2E_ONLY=hints` runs only the mail window hint checks (`run_window_hints`). The labels are fixed per app in `WINDOW_HINT_LABELS`, read from the shots. `E2E_ONLY=popup` runs only the popup key checks (`popup_checks.mjs`): with the thread context menu open by `Shift+F10` and the app menu open by a click, by Enter on its button (Tab from the search box puts the focus there, and a check that the menu opened guards it; Space on the button picks a row in the list) and after an arrow key pressed in it, `j`, `a` and `n` mark, archive and move nothing, and `j` and `k` move the context menu's selection (read as pixels, the same items a real Down and Up reach) and leave the list alone. With Mark highlighted by Home and eight `j`, `l` opens the Mark submenu and `h` closes it (the submenu region against its closed baseline, a real Right and Left reach the same pixels). In the File menu opened by Alt+F with Close highlighted, `l` moves to the Edit menu and `h` moves back (a real Right opens the same menu, apart from the highlighted first item). A click-opened app menu leaves the focus in the list, and `j` and `k` move the menu there as well (read as pixels of the panel), leave the list alone, and `a` and `n` stay swallowed. By keyboard the app menu's focus moves with `j` and `k` the same way. The piece `compose_editor/window` checks the same for the body's context menu in normal and insert mode, and that a `j` typed with the address popup open types. On Betterbird it then clicks DesertBird's toolbar button: `j`, `j`, `k` move the popup's focus ring (read from the pixels of the popup), the thread list keeps its selection, `h` and a click on Help each open the help tab, which takes `q` with no click, and the click closes the popup. Thunderbird gets a NOTE, because its button position is not pinned. It is its own piece, `default/popup`, and runs with the default kind. The Mark submenu draws in a different place on each app, so `popup_checks.mjs` reads a region per app. `E2E_ONLY=page_hints` runs only the page tab hint checks (`page_hints_checks.mjs`), which are the piece `pages/page_hints`. `E2E_ONLY=search` runs only the `/` and `?` search checks (`run_search`). `E2E_ONLY=hud` runs only the which-key, toast and help checks (`run_hud`), after the Inbox opens. `E2E_THEME=dark` or `light` starts the app with that built-in theme and puts the name in the hud screenshots. `E2E_CONSOLE=1` prints the app and add-on console to `app.log`. The hud checks compare the bottom 80 px of the window (`shot_region`): the same selection with no panel draws the same pixels.

Betterbird is `/usr/bin/betterbird`. Override a binary with `--binary thunderbird=/path`. Scratch files go to `<run dir>/<app>/<kind>/<section>/`, see Run dir. `E2E_STARTUP_MS` (default 30000) is the ceiling on the wait after launch, see Startup.

## Pieces

The run is a list of pieces. A piece is one kind and one section: it gets a fresh profile, starts the app, runs its checks and stops the app. Its name is `<kind>/<section>`, and a kind with one section has the section `main`. The timings and the work dir use `<app>/<kind>/<section>`. The check lines keep `<app>/<kind>`, so the PASS names of a kind are the ones the single run printed. Every piece passes when run alone. `piece_runner.mjs` runs one piece, and `run.mjs` loops it over the pieces and the apps.

A piece is an object in a file of `pieces/`: `kind`, `section`, `run(instance, ctx)`, and as needed `profile_kind` (default: the kind), `seeds`, `extra_script` and `prepare(work_dir, kind)` for what the xpi or the work dir needs before the start, `toast_seed` (merges `E2E_SETTINGS`, the shortened toast time), `before_start(ctx)` (runs before the piece's own app starts, and its return value is `ctx.reference`), `opt_in` (not in a run with no setting), and `only` (aliases for `E2E_ONLY`). The hook files take the whole ctx as the helpers they destructured before, so they need no change.

- `E2E_KINDS` is a comma list of kinds. A kind takes all of its pieces apart from the opt-in ones. Unset, it is the list in `registry.mjs`. An unknown kind is an error that lists the kinds.
- `E2E_ONLY` is a comma list of section names or aliases, and keeps the pieces that carry one of them. Names: the sections (`keys`, `page_hints`, `typing`, `main`, `popup`, and the default kind's `window_hints`, `mode_label`, `threads`, `tabs`, `search`, `view_settings`, `filter_by_message`, `cmdline`, `cmdline_launch`, `folders`, `hud`, `followup`, `steps`, `visual`, `panes_focus`, `panes_undo`, `startup_focus`, `panes_chrome`; `scale` is opt-in and needs `E2E_SCALE=1`, see below) and the aliases `hints` (`default/window_hints`), `panes` (the `default/panes_*` pieces and `default/startup_focus`) and `web_hints` for `web/main`, whose filter stays inside `web_checks.mjs`. `keys` and `typing` also select pieces of other kinds, so add `E2E_KINDS` to narrow the list. A name that matches nothing is an error that lists the valid names.
- `E2E_SCALE=1` runs the piece `default/scale` alone: the step keys on a folder of 10,000 messages. The profile builder reads the same variable to add that folder, so naming the piece in `E2E_ONLY` without `E2E_SCALE=1` is an error.

Departures from the single run, each on purpose:

- With `E2E_ONLY` set and `E2E_KINDS` unset, only the matching pieces run. Before, `E2E_ONLY` narrowed the default kind and the other kinds still ran in full.
- `E2E_ONLY=page_hints` no longer runs the typing checks after the hint checks. They are the piece `pages/typing`.
- `E2E_SCALE=1` selects the scale piece alone. Before, it made every kind run the scale code.
- A name in `E2E_ONLY` or `E2E_KINDS` that matches nothing is an error. Before, an unknown `E2E_ONLY` ran everything and an unknown kind ran the no-identity checks.
- The `pages` kind is three pieces, so three app starts: the key checks, the hint checks and the typing checks. Before, one app ran all three.
- `E2E_ONLY=keys` also takes `default/keys`, next to `pages/keys`. Add `E2E_KINDS` to narrow it.
- The popup key checks are the piece `default/popup` and run in a full run. Before, they ran only under `E2E_ONLY=popup`.
- The preamble checks of the default kind (the Inbox opens with keys) repeat in each piece that opens the Inbox.
- The mode label style pieces start their own classic reference app (about 8 s each). Before, they compared against strips that the `default` kind left in a module variable, which a piece run alone or in a worker would lose.
- The default kind is 18 pieces, one per section, so 18 app starts where one run used one. Each starts a fresh profile, so a section no longer leans on the state an earlier one left. The pieces run in the order of their file names. The three that leaned on an earlier section got a setup step: `panes_undo` archives one row first (the older undo step that visual mode's `.` left), `steps` presses `m R` in the Inbox first (so the `m u` message is the only unread one) and `tabs` selects the last row and waits for its pane to load. The check `the next u undoes the older . archive` is now `the next u undoes the older a archive`, and the command line pieces add one check, `the helper shows the Views folder before the command line checks`, because a piece run alone starts in the Inbox.

## Workers

`E2E_SHARDS=<n>` above 1 runs the pieces on `n` forked workers (`worker.mjs`) under one coordinator (`coordinator.mjs`). Unset, it is 1, and the run is the serial loop of `run.mjs`, unchanged. The count is capped at the number of pieces, so a run of one piece stays serial. Each piece already has its own dir, labwc socket, `HOME`, profile and sink port, so two workers never share a display, a home or a port.

- The queue holds one id per app and piece, `<app>/<kind>/<section>`, heaviest first by the weights in `piece_seconds.json`. A newer unfiltered `.logs/e2e-timings-*.json` overrides a weight, and `E2E_WEIGHTS=<file>` names the file. A piece with no weight goes first, with a warning. The first piece of worker `n` goes out `(n - 1) x 500` ms after it is ready.
- Each output line of a worker starts with `[w<n>]`. The PASS and FAIL lines are the ones the serial run prints.
- `E2E_DEADLINE_S` ends the run, counted from the coordinator's start: every worker is stopped, and the report lists the pieces in flight and not started under `incomplete`. Unset, it is derived from the weights of the queue: 1.5 times the larger of one worker's share and the heaviest piece, plus 60 s, and at least 900 s (`derive_deadline_s` in `shards.mjs`). A piece with no weight counts as its piece deadline. A full run of both apps gets about 1,870 s on 3 workers and about 970 s on 6. A fixed 900 s stopped every full run on 3 workers, which takes about 1,300 s. The start line prints the deadline. The target is 300 s, which a full run of both apps reaches only with more workers or shorter pieces (about 3,670 s of pieces in all).
- `E2E_PIECE_DEADLINE_S` (default 120) is the deadline of one piece from its hand-out. A piece may carry its own `deadline_s`. The long ones (`message`, `message_remote`, `pages/keys`, `pages/page_hints`, `own_pages`, `web` and `default/panes_focus`) take `LONG_PIECE_DEADLINE_S` (250) from `registry.mjs`. A piece's deadline is the larger of its own and `E2E_PIECE_DEADLINE_S`, so on a loaded machine one setting raises them all. A unit test fails when a weight times 1.5 passes its piece's deadline. A piece past its deadline fails, its worker gets SIGTERM (SIGKILL after 10 s), the apps of the piece are reaped and a fresh worker takes the queue.
- A worker that dies while it holds a piece fails that piece, its piece dir is reaped (`reap.mjs`) and a fresh worker takes its place while pieces wait. A worker that dies before it is ready is not replaced, so a bad setup cannot loop.
- The coordinator holds the run dir and its lock. A worker gets the path in its `init` message and never opens a dir. SIGINT, SIGTERM and SIGHUP to the coordinator stop every worker (each stops its apps), write the report, free the lock and exit 130, 143 or 129. A worker whose coordinator dies sees the IPC channel close and stops its apps.
- Exit 0 needs every check to pass, no worker failure and an empty queue. A failed check, a worker failure, an incomplete queue or the run deadline exits 1.

Copied from DesertFox's `test/key/` (`run.mjs`, `worker.mjs`, `shards.mjs`, `timings.mjs`), with these departures:

- A piece id is the full `<app>/<kind>/<section>` in the queue, the weights, the ledger and the timings. DesertFox names a piece by its file's basename, which here would fold the pieces into `main` or their section and merge the two apps.
- No debug ports and no session marker. A worker that did not stop cleanly gets its piece dir reaped by command line (`reap.mjs`), since labwc's environment is unreadable.
- Workers hold no app across pieces, so a dead or killed worker is replaced. In DesertFox a shard owns a Firefox session and ends with it.
- A piece deadline, held by the coordinator from the hand-out, on top of the run deadline. The waits inside a piece stand in for DesertFox's per-case limit.
- The coordinator staggers each worker's first piece, where DesertFox delays each worker's start.
- Workers send their checks and timings entries in `piece_done` and write no file. One run dir and one lock, held by the coordinator.
- Signals in both the coordinator and the worker go through `install_lifecycle` (`harness.mjs`), whose `on_signal` hook stops the workers and writes the report before the exit, and whose `announce: false` keeps a worker quiet.
- Setting names are `E2E_*`. `KEY_TEST_ORDER=reverse` is not copied, since the serial run keeps the registry order.
- The default worker count is 1 for `npm run e2e`, where DesertFox runs 8. `just e2e` sets 3, since fleet sessions run at most 3 apps at once (see Scope and lock).

## Changed-only runs

`E2E_CHANGED=1` keeps the pieces that the change can affect. Each piece file has one line, `export const areas = [...]`, with the areas it exercises. `areas.mjs` maps `src/` files to areas (`area_rules`, first match wins) and diffs against `E2E_BASE` (default `origin/main`: commits, working tree and new files). A piece runs when it shares an area with a changed src file. A changed piece file runs that piece. A change to a file in `shared_files` of `areas.mjs` (the manifest, `background/{main,router,notify}.ts`, `commands/{define,index,tab_keymaps}.ts`, the config, `shared/{protocol,swallow,keymap_tree}.ts`, the key runtime, overlay host and focus files of `chrome/`, and the two experiment schemas), `vendor/`, `package.json`, `package-lock.json`, `tsconfig.json`, `tools/build.mjs` or any harness file of `tools/e2e/` runs every piece. The list in `shared_files` is the source. A helper that only some pieces use (`_default_shared.mjs`, `panes_checks.mjs`) runs those pieces. A src file that no rule places runs every piece, and `test/e2e_areas.test.ts` fails on it, so add a rule. A docs-only change runs nothing. The check `registry.select_pieces` makes the choice, and `changed_run_apps` gives `run.mjs` its app list `["betterbird"]` unless apps are named: a changed-only run uses Betterbird alone, and the full run covers both apps. A diff that selects no piece prints `e2e: no pieces selected` and exits 0, serial or sharded.

`node tools/e2e/changed.mjs [base [head]]` or `--paths a,b` prints the pieces and runs nothing. `E2E_CHANGED_PATHS` (a comma list) replaces the git diff.

Departures from DesertFox `test/key/areas.mjs`, each on purpose:

- The pieces are read per file (`areas` sits in the piece file, not the piece object), because one file can hold several pieces (`mode_label.mjs`, `compose_editor.mjs`). The choice is a set of files, and the registry keeps the pieces from those files.
- The selection hook is `E2E_CHANGED=1` in the registry and `just e2e-changed` sets it (the base is `E2E_BASE`), in place of DesertFox's `key-test-changed` taking the base as an argument.
- Betterbird only, because the owner chose one app for a changed-only run.
- The bridge (`src/background/bridge/`) maps to no area, since no piece drives it.
- The harness rule is wider than DesertFox's list: any file of `tools/e2e/` that has no narrower rule selects every piece, so a new harness file errs to the safe side. No src file is unplaced in DesertFox either way, and a src file with no rule selects every piece.
- There is no host rule and no `{setup:true}` case, since DesertBird has neither.

## Scope and lock

`just e2e [args]` takes the lock, then installs, sweeps, builds and runs `npm run e2e -- --xpi dist/desertbird.xpi [args]` on 3 workers (`E2E_SHARDS` overrides) in a capped systemd scope when `systemd-run --user` works. `just e2e-changed [args]` adds `E2E_CHANGED=1` (the base is `E2E_BASE`). `just e2e-sweep` runs the sweep alone. The justfile calls npm, never the reverse.

- Lock: `/tmp/desertbird-e2e.lock`, one run per machine, because two runs break the memory budget. The build sits under it, since a build outside it would delete `dist/` under a run that still reads the xpi. A second run prints the holders and waits up to 3600 s, then fails. Never wrap the recipe in `flock`.
- Scope: `MemoryMax` of 2 GB per worker plus 2 GB (8 GB on 3 workers), `MemoryHigh` 1 GB under it, no swap. The runtime limit is the run deadline plus 120 s. `run.mjs --print-deadline` prints the deadline, which is `E2E_DEADLINE_S` or the one derived from the weights. A run with no deadline (serial, or one piece) gets 7200 s. The scope joins `agents.slice` when the caller is in it. With no systemd user session the run goes on without a cap and says so.
- Sweep (`sweep.mjs`): under the lock, it kills the process groups of any `desertbird-e2e-*` dir in the temp dir that hold a command line with `-profile <dir>/...` or `-C <dir>/...`, which is what a run starts, and the session keyboard holder (`wtype -s`, which names no dir) of any such dir, found by `XDG_RUNTIME_DIR` in `/proc/<pid>/environ`. A worker that dies mid-piece gets its holder reaped the same way. It takes each dir's lock while it reaps, so a live run is skipped and an `E2E_DIR` run cannot start mid-reap. A reader of the kept logs (`less`, `rg`), a dir from `E2E_DIR` and anything else (the owner's Betterbird, `~/.thunderbird`) is left alone. The dirs stay as evidence.

Departures from DesertFox's `key-test` recipe:

- The lock wait is 3600 s, not 900 s, for the longer run. A full run takes about 20 minutes, so waiting beats failing.
- The runtime limit is the deadline plus 120 s, where DesertFox adds 70 s. The extra 50 s covers the worker stop grace (10 s), the app stops and the report, which run longer here. A run with no deadline gets 7200 s.
- `MemoryMax` scales with `E2E_SHARDS`, where DesertFox fixes 16 GB and 14 GB for its 8 shards. No `CPUQuota`: `agents.slice` already caps the CPU.
- The sweep runs in the recipe under the lock, where DesertFox's `run.mjs` sweeps itself. It finds a run by its dir and lock, where DesertFox reads an owner file.
- No `build-key-test` step: the run uses the one build, made under the lock.

## Startup

Each app runs in its own headless labwc session (`tools/measure/session.mjs`), which has no input device. Each `wlrctl` click and `wtype` run adds a virtual one and drops it, so without help the seat lost its keyboard at every click, and the app's new `wl_keyboard` sometimes got no enter event and dropped every key until the next click (issues #139 and #178). The session starts one `wtype -s 86400000` beside labwc, in its own process group, to keep a keyboard on the seat for the whole run. `stop` ends it with labwc, and a failed start stops it too. `test/tools/session_keyboard.test.ts` checks the seat keeps its keyboard after a key and a click, and that stop and the sweep end the holder.

`start_app` and `restart` return when the app is ready, not after a fixed wait. Ready is two steps. First the helper add-on answers `state` with DesertBird enabled and a mail tab. Then a key probe: Escape, `w`, `m` flips the message pane and the helper sees the flip. The probe is pressed until a press lands, because a key before the first paint and focus is dropped. It then presses until the pane is back as it was and has held that value for 1.5 s. `restart` waits for the old process to exit and clears the old reply file before it asks, so a stale answer never counts. If the ceiling `E2E_STARTUP_MS` passes first, the start fails with the stage it was in and the log path. A start with no helper add-on (the setup proof without `--xpi`) has nothing to ask and keeps the fixed wait.

## Waits

A key is not followed by a fixed sleep where the helper add-on can read its result. `ctx.mjs` has these helpers, ported from the DesertFox key-test harness (`poll_until`, `barrier`, `expect_absent`):

- `wait_state(instance, what, until, options)` asks for `state` until `until(state)` holds. It starts with `wait_for`, which takes any read. `key_and_state(instance, keys, { what, until })` presses and waits. A number as the third argument is the older fixed wait, which the sections not yet ported still use. `selects(id)`, `flag_becomes(id, name, value)` and `compose_opens(tab_is_ready)` build the common waits.
- `open_key_list(instance, { slug, list_before })` presses `g ?` and waits for the key list to draw. It makes one attempt. The session keyboard holder (see Startup) closed the gap behind issue #139, where keys never reached the window after a click.
- `barrier(instance)` presses Escape, `w`, `m` and waits until the helper sees the message pane flip, then `w`, `m` again and waits until it flips back. This is the key probe of the startup. It needs the focus in the thread list. The app stores the pane state in the profile, and a restart ends the app with SIGTERM, which can keep the hidden pane of the first flip. So `restart_app` shows a hidden pane again and records a NOTE. `expect_absent(instance, name, found, { margin_ms, in_list })` records a check that nothing happened: it waits `margin_ms`, then takes the barrier where `in_list` holds (else one state read), and `found(state)` returns what appeared, or null.
- A fold has helper state of its own: a collapsed thread root selects its whole thread and an open one selects only itself. `run_threads` waits on that count (`thread_shows`) after each fold.
- `measure_barrier` runs first in `run_threads` and records a check that an `l` or `h` fold pressed before the barrier has landed when the barrier returns. A miss would mean the barrier is too weak for the negative checks.

- `wait_pixels(instance, what, name, region, until, options)` polls the hash of a screen region, 100 ms apart, for what has no helper state: the which-key panel, the toast strip, the command line, the mode label, the window hint labels. `drawn_since(baseline)` ends when the region shows something other than the baseline and holds it for two reads, `back_to(baseline)` when it matches the baseline again, and `holds_twice()` when it stands still. A poll never records a FAIL of its own, because the check after it judges the hash. A baseline always comes from the same section and the same read just before the key. `open_command_line` and `press_in_command_line` press keys and wait on the drawn line, and `close_command_line` presses Escape until one changes nothing.
- A toast of a refused command lasts `toast_error_ms`. The runs of the kinds that wait for it (`default`, `reply_no_identity`, the quick reply kinds) seed 3 s (`E2E_SETTINGS` in `profile.mjs`) into the storage of the add-on, and `src/` keeps its default. Nothing shows that no toast is up, so a read that needs a bare strip waits `TOAST_EXPIRY_MS` after the last toast key. `profile.mjs` also sets `ui.caretBlinkTime` to 0: a blinking caret gave the command line two hashes in turn.

Departures from DesertFox:

- A wait that times out does not throw. It records `FAIL wait for <what>` with the last read and returns that read, so the check after it reports the value and the checks behind it still run. `soft` waits only settle a state and record no FAIL. DesertFox throws, because a case there is one unit.
- DesertFox reads a key-event feed from the page, so its barrier waits for the page to report the key. DesertBird has no such feed and no test hook in `src/`, so its barrier is a key with an effect the helper reads. The flip proves that the keys before it reached the key runtime. It does not prove that a background command pressed before it has finished, because the background page runs each key's command on its own: a fold makes four Experiment calls, the pane toggle two. The two flips and their reads leave time for a short command, and `measure_barrier` checks that on the fold path. A negative check also keeps the fixed wait it had before the polled waits as `margin_ms`, because a refused or unbound key has no completion signal: `s`, `m x` and `1` (1.2 s), the `C-l` refusal (1.5 s), `a` typed in the quick filter (1.5 s, after the list empties), `j` in the message body (2.5 s) and no junk after the motions (1.5 s).
- The wait time is counted in the `wait_stats` of the piece's ctx, and each default piece prints it as the NOTE `polled waits` at its end, not in a `waits` bucket of `timings.mjs`.
- The helper add-on polls the sink every 50 ms (it was 200 ms), because the gap is the floor of every wait. It also reports `focused` for each window, which `close_compose` waits on.
- Fixed waits that stay, because the keys go where the barrier cannot follow or no helper state shows the result: the open context menu (it swallows `w` and `m`, and Escape would close it), the focus move into the quick filter and into the message body and back, the scroll keys `z t`, `z z` and `z b` before their shots (the barrier would show the message pane and move the rows), the new message tab before its shot, and the 1.5 s after a folder opens in `open_inbox`, where the status bar still shows "Done" and a pixel read in a later check would include it, the hold that the key running a window hint command starts (`HINT_HOLD_MS`, counted from that key, nothing shows when it is over), the quiet window after an Escape that closes the command line, and a key that is typed before the command line is ready and must be dropped.
- Pixel waits: `wait_message_loaded` waits for a body report whose text names the newly selected fixture message (sent 1.5 s after its document loads), then until the status bar text area draws the same as a blank stretch of the bar. The report comes first because the bar is also blank before "Loading Message..." shows.

## Timings

Every run writes `$E2E_TIMINGS_FILE` (default `<repo>/.logs/e2e-timings-<stamp>.json`, and the report goes beside it as `<same name>.report.json`) after each piece. It has the shape of the DesertFox key-test report. `pieces` holds one entry per piece run (`<app>/<kind>/<section>`, with its app starts as `startups` and its peak memory as `peak_memory_kb`; a piece that starts a reference app lists its startups and peak memory under `reference_apps`, one entry per extra app). A startup entry has `first_poll_ms`, `first_answer_ms`, `mail_tab_ms`, `enabled_ms` and `keys_live_ms` from the launch, and the `ceiling_ms` it would have waited. Memory is the sum over the app's process group, so content processes count. `rss_kb` counts shared pages in every process, `pss_kb` splits them. `timings.mjs` holds the sampler. A run narrowed by `E2E_KINDS`, `E2E_ONLY` or `E2E_SCALE`, or run with no `--xpi`, records that in `filter`, and `npm run e2e:weights` refuses its file. It also refuses the file of a sharded run, since pieces run up to twice as long beside other workers, and the weights feed the piece deadline test. With no file named it takes the newest serial one. A full serial run prints a `stale weight` line for each piece far over its committed weight. A sharded run prints the same comparison as `slower than its weight`, with no hint to refresh.

A sharded run writes one merged file at the same path. Each piece entry gains its `worker`, and a piece the coordinator cut off has `timed_out`, `died` or `in_flight` set. The file adds `workers` (busy and idle time and the pieces of each), `critical_worker` (the one that finished last), `incomplete` when pieces did not run, `failed_checks`, `failures` and `exit_code`. The checks, shots and notes of the report go in registry order, apps first, whatever order the workers finished in, and each names its `piece` and `worker`. The run prints a summary: each worker, the 15 slowest pieces, the failed checks by piece, and any incomplete pieces.

`node tools/e2e/measure_concurrent.mjs [thunderbird|betterbird] --xpi dist/desertbird.xpi [--counts 1,4]` starts that many apps at once per round (default 1, then 4), each in its own session and fresh profile, and writes startup times and peak memory to `concurrent.json`. It sizes the worker count for a parallel run. It always works in a new `mkdtemp` folder and ignores `E2E_DIR`, because the e2e start code deletes the profile and out folders it is given. It refuses an `E2E_CONCURRENT_FILE`, work, profile or out path outside that folder. `E2E_CONCURRENT_FAIL_LAST=1` makes the last app of each round fail after it starts, to show that every session still stops.

## Flake history

`just e2e-flakes <n> [app...]` is the way to run it: it installs, takes the `just e2e` lock, sweeps the apps of dead runs, builds once and runs the batch in one systemd scope with the memory cap of `just e2e` and a time limit of `n` run limits. `npm run e2e:flakes -- <n> [thunderbird|betterbird]...` is the batch itself and takes no lock, sweeps nothing and sets no cap. A SIGINT, SIGTERM or SIGHUP goes on to the running `run.mjs`, which stops its apps, and the batch then ends with 130, 143 or 129 and records nothing. The history line names the revision read before the build. It builds once, then does `n` full runs with `--xpi dist/desertbird.xpi` (`E2E_SHARDS` defaults to 3 here, and the default of `npm run e2e` is unchanged). Each run writes its merged timings file and its log to `.logs/e2e-flakes-<stamp>/`. `flakes.mjs` folds the files into one JSON line (runs, clean runs, run errors, and each failed check by full piece id with the number of runs it failed in), appends it to `~/.local/state/desertbird/e2e-flakes.jsonl` (`E2E_FLAKES_HISTORY` overrides) and prints a summary. It exits 1 and sends a `notify-send` alert when a check fails in 2 or more runs or 3 or more runs error. A check that fails in every run is reported as broken, not flaky. A run with no merged file (setup failed or the run died) is a run error. A selection of a single piece runs serially and writes no merged file, so a batch needs at least two pieces. An `E2E_SHARDS` below 2 or not a number is refused before the build, since a serial run writes no merged file. A piece that the coordinator reports as died or timed out counts as the case `(piece failure)` of its piece id. `node tools/e2e/flakes.mjs fold <commit> <timings file>...` folds files from runs you made yourself.

It follows DesertFox's `test/key/flakes.mjs` with these departures: the history is `e2e-flakes.jsonl` under `desertbird`; the runner is a node command (`npm run e2e:flakes`), not a `just` recipe that loops in shell; it reads `failed_checks` of the merged timings file, since DesertBird has no failed-case or lost-key list, so a case has no suspect count; a case is keyed by the full piece id `<app>/<kind>/<section>`; the node command has no `sweep` and no `flock`, because each run makes a fresh work dir with its own lock and a pass removes it, and the `just` recipe takes the shared lock and sweeps before the batch; the alert names a check that fails in every run as broken; the default batch is the number the caller gives, with no default of 10, since a run takes about 20 minutes.

## Run dir

Each run prints `e2e: work dir <path>` first. With `E2E_DIR` unset the dir is a fresh `mkdtemp` folder, `desertbird-e2e-*` under the temp dir. It holds scratch files and screenshots only. A pass removes it. A failure, or `E2E_KEEP=1`, keeps it for the logs, and the run prints `kept`. A kept dir stays until you remove it. A dir named by `E2E_DIR` is never removed. A run takes `run.lock` in its dir with its pid and start time and refuses a dir that a live run holds. A lock of a dead run is taken over. `E2E_DIR` may not be a real home dir (the passwd one or `$HOME`), a dir above it or a dir in `~/.thunderbird`.

Before an app starts, `start_app` resolves its work dir, profile, out, home and runtime paths through their symlinks and throws unless each is in the run dir, before it removes anything. `assert_app_isolated` (`run_dir.mjs`) then throws unless `HOME` and the runtime dir are in the run dir, `HOME` is not a real home or in `~/.thunderbird`, and `WAYLAND_DISPLAY` is a socket in the run dir's runtime dir. SIGINT, SIGTERM and SIGHUP stop every app of the run, wait out the kill grace, release the lock and exit 130, 143 or 129. A later signal waits on the same shutdown. An uncaught error kills every app group and releases the lock. A SIGKILL of the serial runner leaves its apps running, which PR 7's systemd scope is meant to end. A sharded run's workers stop their apps when the coordinator dies.
